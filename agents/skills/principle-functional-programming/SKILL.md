# Principle Functional Programming

関数型プログラミングの狙いは、業務のルールを、副作用から切り離した小さな関数の組み合わせとして表すことにある。
そうすると、ルールが型と関数の名前から読み取れるようになり、テストも入力と出力だけで書けるようになる。
このスキルの方針は、この狙いから導かれている。

## 適用の範囲

まず、対象のプロジェクトと言語の書き方を確かめる。

| 状況 | 方針 |
|---|---|
| TypeScript / JavaScript | 関数型で書くことを勧める。ただし、プロジェクトに確立した書き方があればそれに従う |
| クラスを中心に設計する言語やプロジェクト（Java、C#、クラスベースのフレームワークなど） | 関数型の書き方を無理に持ち込まない。プロジェクトの書き方に合わせる |
| `Error` のサブクラス、フレームワークがクラスを要求する箇所（Web Components、DI コンテナ、ORM のエンティティなど） | フレームワークに従う。その内側のロジックだけを純粋関数に切り出す |

クラスを中心とするプロジェクトでロジックを切り出すときは、次のようにする。

- 純粋関数は、クラスのメソッドではなく別のモジュールの関数として置く。プロジェクトに慣習があればそれに従う
- 依存の注入、端での時刻や乱数の取得は、プロジェクトの既存のやり方（コンストラクタ注入など）に合わせる。時刻を注入する仕組みがなければ、端のメソッドで判断より前に1回だけ取得して純粋関数に渡す（同じ処理の中で、判断の前提になる時刻を揃えるため）。頼まれていない仕組み（Clock のプロバイダなど）は新しく作らない
- 小さな変更では、既存の型（エンティティなど）をそのまま使う。依頼されていない状態の型やブランド型は新しく導入しない

クラスを中心とする書き方に合わせる場合でも、純粋なロジックを I/O から分ける、状態を破壊的に変更しない、といった考え方は、その言語の書き方の範囲で活かせる。
書き方を混ぜてコードベースの一貫性を壊すほうが、関数型にしない損失より大きい。

## 基本方針

### 1. 業務のモデルを型で表し、状態ごとに型を分ける

業務で扱うものは、その状態ごとに別の型として表す。
たとえば注文なら、「未検証の注文」「検証済みの注文」「価格計算済みの注文」を別々の型にする。
状態をフラグや省略可能なプロパティで表すと、ありえない組み合わせ（未検証なのに価格がある、など）が型の上で許されてしまう。

詳細は [references/domain-modeling.md](references/domain-modeling.md) を読むこと。

### 2. 処理は、状態を遷移させる純粋関数として表す

業務の処理は、ある状態の型を受け取り、次の状態の型を返す純粋関数として書く。
業務フロー全体は、その関数をつないだパイプラインになる。

純粋関数とは、同じ入力に対して必ず同じ出力を返し、副作用（I/O、引数や外部の変数の書き換え、現在時刻や乱数の取得）を持たない関数である。

- 引数を書き換えない。新しい値を返す（`push`、`splice`、プロパティへの再代入をしない。スプレッド構文で新しいオブジェクトや配列を作る）
- 状態を関数の外に隠さない。必要な値は引数で受け取る
- 現在時刻や乱数は、関数の中で取得せず引数で受け取る

### 3. I/O は端に寄せる

DB、外部API、ファイル、ログ、画面の操作などの I/O は、処理の最初と最後に寄せ、純粋関数の中に混ぜない。
I/O の途中で判断が必要になり、どうしても端に寄せきれない場合は、I/O と純粋な処理を交互に並べる「サンドイッチ」の形にする。

詳細は [references/io-and-dependencies.md](references/io-and-dependencies.md) を読むこと。

### 4. 依存はカリー化で注入する

I/O を行う関数が依存（DB の接続、外部APIのクライアントなど）を必要とするときは、依存を先に受け取り、業務の入力を後から受け取るカリー化した関数にする。
依存は、アプリケーションの起動時など1か所でまとめて渡す。
関数型で書くプロジェクトでは、クラスやDIコンテナは使わない（クラスを中心とするプロジェクトでは「適用の範囲」に従う）。

詳細は [references/io-and-dependencies.md](references/io-and-dependencies.md) を読むこと。

### 5. 業務上の失敗も、業務のモデルとして表す

業務上起こりうる失敗（入力が不正、在庫が足りない、など）は、業務の言葉で名前を付けて型に表す。
Result 型のような汎用の型を使うか、失敗を表す状態の型を返すか、例外を使うかは、プロジェクトの書き方に従う。
大事なのは、どんな失敗が起こりうるかが型や関数のシグネチャから読み取れることである。

### 6. 関数に切り出すのは、切り出す理由があるときだけにする

純粋関数で書くことと、処理を細かい関数に分けることは別である。
1か所でしか使わない短い処理は、その場に書く。読み手は呼び出し先へ移らずに、上から順に読める。

関数に切り出すのは、次のどれかに当たるときだけにする。

- 業務のルールや判断で、名前を付けると意図が伝わり、単独でテストしたいもの（状態の遷移はこれに当たる）
- 同じ処理を、複数の場所で使う
- I/O と純粋な処理を分けるため（端の処理から判断を取り出す）
- 処理が長く、その場に書くと流れが読めない

次のような関数は作らない。

- 1行の式に名前を付けただけで、1か所でしか使わないもの（`const isEmpty = (items) => items.length === 0` など）
- 標準の関数やほかの関数を、そのまま呼ぶだけのもの
- 業務の状態の遷移ではなく、手順の途中を区切っただけのもの

迷ったら、その場に書く。2か所目で必要になったときに切り出せばよい。

## 実装するときの手順

1. **適用の範囲を確かめる。** 言語とプロジェクトの既存の書き方を読み、関数型で書くかどうかを上の表で判断する。関数型で書かない場合も、純粋なロジックと I/O の分離だけは検討する。
2. **業務フローを言葉で書く。** 「何を受け取り、どの状態を経て、何を出力するか」を、業務の言葉で一続きの流れとして書く。
3. **状態ごとの型を定義する。** 流れの中の各状態を型にする。ありえない組み合わせが型で表せないようにする。
4. **状態を遷移させる関数を書く。** 状態の遷移ごとに純粋関数を書き、つないで業務フローにする。遷移の中の短い計算は、基本方針6に従って関数に切り出さず、その場に書く。
5. **I/O を端に置く。** 取得と保存などの I/O を、純粋な業務フローの前後に置く。端に寄せきれなければサンドイッチの形にする。
6. **依存をカリー化で注入する。** I/O を行う関数は依存を先に受け取る形にし、エントリポイントでまとめて渡す。
7. **セルフレビューする。** 下のチェックリストで確認する。

既存コードを関数型に書き換えるのは、ユーザーがリファクタリングを求めた場合だけにする。
それ以外は、新しく書く部分と、変更のために触る部分に限る。

## リファクタリングを頼まれたとき

既存コードを関数型に書き換えるよう頼まれたら、外から見た振る舞い（戻り値、保存や送信の内容と順序）を変えない。

- **振る舞いを担っている状態は消さない。** モジュールのトップレベルのキャッシュなど、消すと振る舞いが変わる状態は、端のクロージャに閉じ込めて注入する。消すべきかどうかは質問として挙げる
- **副作用の時機や回数の変化を報告する。** 時刻や乱数の取得を端に移すと、呼ばれる時機や回数が変わることがある。その変化と、外から観察できるかどうかを報告に書く
- **読み取りと更新の間に `await` を足さない。** 元のコードで同期的に続いていた読み取りと更新の間に `await` を入れると、同じプロセスの中での順序の保証が失われる
- **疑わしい振る舞いは直さない。** 不具合に見える点も、仕様の確認点として挙げるにとどめる

終わったら、次の4点を報告する。

1. 変更後のコード
2. 変更の内容と理由
3. 呼び出し側への影響
4. 仕様の確認点（疑わしい振る舞い、残した状態を消すべきか、副作用の時機の変化など）

## レビューのチェックリスト

関数型の観点でのレビューを頼まれたら、次の観点で確認し、下の「レビューの出力」の形式で返す。
プロジェクトがクラスを中心に書かれている場合は、関数型への書き換えを指摘しない。

### 適用の範囲

- [ ] プロジェクトの既存の書き方と一貫しているか。関数型の書き方を無理に持ち込んでいないか

### モデリング

- [ ] 業務の状態ごとに型が分かれているか。フラグや省略可能なプロパティで状態を表していないか
- [ ] ありえない状態の組み合わせを、型が許していないか
- [ ] 型と関数の名前に業務の言葉が使われているか
- [ ] 起こりうる業務上の失敗が、型やシグネチャから読み取れるか

### 純粋さ

- [ ] 業務のロジックが純粋関数になっているか
- [ ] 引数や外部の変数を書き換えていないか
- [ ] 現在時刻・乱数・環境変数を、関数の中で直接取得していないか

### 関数の切り出し

- [ ] 1か所でしか使わない短い処理や、ほかの関数を呼ぶだけの関数を切り出していないか。切り出すなら、業務のルール、再利用、I/O との分離、長さのどれかの理由があるか

### I/O と依存

- [ ] I/O が処理の端に寄っているか。純粋関数の中に I/O が紛れ込んでいないか
- [ ] 依存がカリー化で注入されているか。モジュールの中で依存を直接 import して使っていないか
- [ ] 依存をまとめて渡す場所が1か所に集まっているか

## レビューの出力

レビュー結果は次の形式で返す。

1. **要約**: 全体の評価と、最も重要な問題を2〜3行で書く
2. **指摘**: チェックリストの項目（箇条書きの1行）ごとに1件とし、重要度の高い順に並べる。どの項目にも当たらない指摘は、最も近い項目に含める。1件ずつ、対象（該当行）、問題、理由、修正案（コードまたは手順）を書く
3. **修正後のコード例**: 指摘をまとめて反映した形を、純粋な中心・端・エントリポイントに分けて示す。元の挙動は保ち、仕様として疑わしい点は直さずに「仕様の確認点」に回す。指摘が小さく、個々の修正案で足りる場合は省く
4. **仕様の確認点**: レビュー中に見つけた、仕様として疑わしい点や前提にした点。なければ省く
