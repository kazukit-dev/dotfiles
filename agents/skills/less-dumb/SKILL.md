# Less Dumb

複雑さの多くはコードではなく仕様から来る。仕様が決まったあとにいくらリファクタリングしても、仕様が要求する分岐・状態・例外処理は消えない。だから一番効くレバーは「その仕様は本当に要るのか」を問うことだ。

このスキルの役割は、最終的な目的と現在の仕様を突き合わせ、目的への貢献に比べてコストが重すぎる仕様を見つけて、より単純な仕様を提案すること。コードの書き方を整えるのは別の仕事（コードレビューや simplify の領分）なので、ここでは扱わない。

## 基本姿勢

- **判断するのはユーザー。** 仕様には、コードからは見えない事情（顧客との約束、法的要件、過去の障害）が隠れていることがある。提案はするが、合意なしに仕様を変えて実装しない。
- **物差しは目的。** 「シンプル」自体は目的ではない。目的を達成できなくなる簡素化は改悪だ。逆に、目的に効いていない仕様は、どれだけ作り込まれていても削る候補になる。
- **削除は大胆に提案する。** 削った仕様の一部を後で戻すことになるのは、削り方が足りている証拠だ。一度も戻さないなら、残すべきでないものまで残している。確信が持てない削除案も、確度と戻しやすさを添えて出してよい。決めるのはユーザーなので、出し惜しみするより判断材料を渡すほうが役に立つ。
- **偉い人・賢い人が決めた仕様ほど疑う。** 権威のある人の要求は誰も疑わないまま残りやすい。出どころが誰であっても、目的への貢献で評価する。
- **提案が無いなら無いと言う。** 仕様が目的に対して妥当なら「このままでよい」と短く伝える。無理に提案をひねり出すと、ノイズでユーザーの判断を邪魔する。線引きは、「失うもの」と「目的への影響」を具体的に書ける案は確度が低くても出し、書けない案は出さない。仕様がおおむね妥当で軽微な案しかないときは、先に「仕様は妥当」という結論と理由を書き、案はそのあとに確度を添えて出す。

## 進め方

### 1. 目的を一文で言う

仕様ではなく、その先にある目的を書く。「誰の、どんな困りごとを、どうなれば解決とするか」。

- 手段と目的を分ける。「CSV エクスポート機能を作る」は手段で、目的は「経理が月次集計を Excel でできるようにする」かもしれない。
- 依頼に目的が書かれていないことは多い。推測できるなら、推測した目的を「前提」と明記して先に進み、出力の「確認したいこと」の先頭でその前提を確かめる。止めて聞くのは、考えられる目的が複数あり、どれを取るかで提案全体の結論が変わるときだけにする。一部の提案の評価だけが変わるなら止めず、その提案に「目的が〜なら評価が変わる」と注記する。目的以外の前提（技術的な前提、法令・監査の要件など）が不明なときも同じように扱う。目的が曖昧なまま仕様を削ると物差しなしで判断することになるが、毎回止めると提案という判断材料そのものが届かない。

### 2. 仕様を要素に分解する

仕様を「〜できる」「〜のときは〜する」の単位に分け、それぞれについて考える。

- **どの目的に効いているか。** どの目的にも結びつかない要素は、最有力の削除候補。
- **コストは何か。** コード量だけでなく、状態の数、分岐、外部依存、テストケース、運用・監視、ドキュメント、将来の変更のしにくさも含める。
- **誰が求めたか。** 要求には、理由を説明できる具体的な人がいるはずだ。「チームの方針」「セキュリティ上」のように部署や一般論にしか辿れない要求は、誰も中身を検証していない可能性が高い。仕様書から辿れなければ、ユーザーに「これは誰の要望か」を聞く。
- **出どころは何か。** 実際に起きた要望か、「念のため」「将来使うかも」「他のサービスにあるから」「前からそうだったから」か。後者は根拠が弱い。

すべての要素を表に並べる必要はない。コストが大きいもの、出どころが怪しいものに集中する。

**本質とのコスト比を見る。** 目的だけを満たす最小の版（素材にあたる部分）を思い浮かべ、今の仕様の実装コストと比べる。核心はクエリ1本で済むのに実装が数千行になる、といった比の大きい箇所は、仕様か作り方のどちらかが複雑すぎるサインだ。類推（「他社はこうしている」）ではなく、目的と制約からゼロで組み立てたらどうなるかを基準にする。

### 3. 疑う

疑う順番が大事で、**削除 → 簡素化 → 高速化・自動化** の順に考える。よくある失敗は、本来なくてよい仕様をきれいに作り直したり、自動化したりしてしまうことだ。まず「なくせないか」を問い、残ると決まったものだけを簡単にする。自動化や汎用化は、仕様と手順が固まって何度も繰り返すことがわかってからでよい。

次の問いを、上から順に当てはめる。全部を機械的に回す必要はなく、効きそうなものを選ぶ。

| 観点 | 問い |
|---|---|
| 削除 | これがなくても目的は達成できるか。誰が、どれくらいの頻度で使うのか |
| 手順の削除 | 承認、確認ステップ、二重チェック、中間ファイルなど、プロセスそのものをなくせないか |
| 先回り | まだ存在しない要望のための汎用化・設定項目・拡張ポイントではないか |
| 例外処理 | そのエッジケースは実際に起きるか。起きたらエラーで止める、または手作業で対応するだけで足りないか |
| 要求水準 | リアルタイムでなくバッチで、完全一致でなく近似で、全件でなく直近だけで足りないか |
| 選択肢 | モード・オプション・設定を1つに決め打ちできないか |
| 状態 | キャッシュ、同期、双方向更新、楽観ロックなど、状態を持つ仕組みをなくせないか |
| 自前実装 | 標準ライブラリ、プラットフォームの機能、既存のサービス、人手の運用で代替できないか |
| 互換性 | 古い形式・古い挙動を維持する必要は本当にあるか。移行して捨てられないか |
| 段階 | 最小の形で出して、要望が出てから足すのではだめか |
| 自動化 | 手順が固まる前に自動化・汎用化しようとしていないか。まず手で回して、繰り返しが見えてから自動化できないか |

### 4. 提案する

効果の大きい順に並べる。効果が同程度なら、削除案を簡素化案より先に置く。案どうしに依存や排他があるときは、見出しに「（案1を採らない場合）」のように条件を書く。各案には次を書く。

- **変える仕様**: 何を削る・変える・決め打ちするか
- **減るもの**: コード量、状態、分岐、依存、テスト、運用のうち何がどれくらい減るか。見積もりなら見積もりと書く
- **失うもの**: 誰のどんなケースが不便になるか、どんなリスクが増えるか
- **目的への影響**: 目的は引き続き満たせるか
- **戻しやすさ**: 必要になったら後から足せるか。高い＝コードを足すだけで戻せる、中＝データ移行や利用者への告知が要る、低＝公開 API や保存済みデータに影響して事実上戻せない。低のものは慎重に

「失うもの」を正直に書くことが一番大事。ここを省くと、ユーザーは判断できない。戻しやすい削除は「まず削って、困ったら戻す」で試せるので、積極的に勧めてよい。

## ほかの依頼と一緒に使うとき

このスキルは、別の成果物（実装方針、実装、レビュー）を頼まれた場面で発動することが多い。依頼された成果物を仕様の話で置き換えない。どこまで進めるかは依頼の種類で決める。

| 依頼 | 進め方 |
|---|---|
| 設計・実装方針の相談 | 簡素化の提案を先に出し、元の成果物は採否が決まるまで保留する。代わりに、仕様をそのまま残す場合に設計の焦点になる点を出力フォーマットの「元の仕様のまま進める場合」に1〜2行書き、どちらを選んでも次に進めるようにする |
| 実装・レビュー | 依頼された作業は最後までやる。仕様の提案は成果物とは別の節にし、下の短い形式で添える。観測される実害（バグ、表示の食い違いなど）は、原因が仕様にあっても成果物の側（コードの指摘）に書く。仕様の節には「その実害を生む仕様は要るのか」という問いだけを書く。例: 「管理者だけ最新の価格が見え、顧客には古い価格が出る」はコードの指摘に書き、「管理者バイパスという仕様は要るのか」は仕様の節に書く |

短い形式は次のとおり。全項目のフォーマットはレビューの中では長すぎて、本来の指摘が埋もれるため。

1. 兆候と、その原因と思われる仕様、前提とした目的（1〜3行）
2. 案は効果の大きい上位3件まで。各案は「変える仕様／失うもの／戻しやすさ」だけ
3. 確認したいこと
4. 深掘りするかはユーザーに任せる、という一文

ユーザーへの質問（目的の前提、誰の要望か）を理由に作業を止めない。質問は「確認したいこと」にまとめ、出せるところまで出す。止めてよいのは、手順1の「目的の解釈で提案全体の結論が変わる」ときだけ。

### 実装中・レビュー中に気づく兆候

次のような兆候に気づいたら、コードを書き進める手を止めて、仕様の簡素化を考える。

- 同じ種類の特例や `if` が何度も追加されている
- フラグや設定項目が増えている
- 同じ問題へのワークアラウンドを重ねている
- テストを書くのに大量のセットアップやモックが要る
- 「念のため」「将来のために」という理由で書いているコードがある
- 性能改善やリファクタリングをしようとしている対象が、そもそも要るのか確かめていない

## 出力フォーマット

仕様の相談、設計・実装方針の相談で使う形式。実装・レビューの途中で使うときは、上の短い形式を使う。

```markdown
## 目的
<一文。推測した場合は「（前提）」と付ける>

## 簡素化の提案

### 1. <見出し：何をどう変えるか>
- 変える仕様: ...
- 減るもの: ...
- 失うもの: ...
- 目的への影響: ...
- 戻しやすさ: ...

### 2. ...

## そのままでよいと判断したもの
- <仕様要素>: <理由を一行で>

## 確認したいこと
- <目的や前提について、ユーザーにしか答えられない質問>

## 元の仕様のまま進める場合
- <ユーザーが設計案・実装方針という成果物を求めたとき（「実装方針を考えて」「どう作ればいい？」）だけ書く。簡素化できるかだけを聞かれたときは省く。保留している成果物と、仕様を変えない場合に設計上いちばん難しい点を1〜2個>
```

「そのままでよいと判断したもの」「確認したいこと」「元の仕様のまま進める場合」は、該当がなければ省く。提案がひとつもない場合は「目的に対して仕様は妥当」と書き、そう判断した理由を短く添える。

## 例

**依頼**: 「通知設定画面を作りたい。メール・Slack・プッシュの3チャネル、イベントごとにオン/オフ、通知時間帯の指定、ダイジェスト配信（即時/日次/週次）に対応して」

**目的**: ユーザーが重要なイベントを見逃さず、かつ通知が多すぎて煩わしくならないようにする。

**提案の例**:

1. ダイジェスト配信を日次だけに決め打ちする
   - 減るもの: 配信スケジューラの分岐、週次集計のロジックとテスト
   - 失うもの: 週次を望むユーザーは、日次を受け取るか即時に切り替えるしかない
   - 目的への影響: 「多すぎない」は日次でも満たせる
   - 戻しやすさ: 高い。配信頻度の選択肢は後から足せる
2. 通知時間帯の指定をやめ、端末側のおやすみモードに任せる
   - 減るもの: タイムゾーンの処理、保留キュー、時間帯をまたぐ配信のテスト
   - 失うもの: メールや Slack には端末のおやすみモードが効かない
   - 目的への影響: プッシュ通知では満たせる。メールと Slack の扱いは要確認
   - 戻しやすさ: 高い。保存済みの設定データがないので、後から時間帯指定を足しても移行は要らない
