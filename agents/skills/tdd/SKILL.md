# TDD Skill

## 絶対ルール

- プロダクションコードを先に書かない。まず失敗するテストを書く
- 失敗を確認していないテストを、実装理由にしてはいけない
- 1サイクルで扱う振る舞いは1つだけにする
- Greenでは、テストを通すための最小限の変更だけを行う
- Refactorは、すべてのテストがGreenのときだけ行う
- Refactor中に振る舞いを追加しない。新しい振る舞いは次のRedから始める
- テストが壊れたまま次のTODOへ進まない
- まとめて複数のテストを書かない。次の一歩を示すテストを1つ書く

## 実行サイクル

1. TODOリストを書く
2. 次に実装する小さな振る舞いを1つ選ぶ
3. 失敗するテストを1つ書く（Red）
4. 最小限の実装で成功させる（Green）
5. テストが通ったまま設計を整える（Refactor）
6. TODOリストを更新する
7. 目的の振る舞いを満たすまで繰り返す

## TODOリスト

- 実装前に、分かっている振る舞い・制約・境界条件・例外ケースを書き出す
- TODOは1つのRed-Green-Refactorサイクルで完了できる大きさにする
- 大きすぎるTODOは、最初に通せる最小の例へ分割する
- 作業中に発見したTODOは追加・分割・並べ替える
- 完了したTODOと残TODOが分かる状態を保つ

## Red-Green-Refactor

### 1. Red

次のTODOから、もっとも小さい振る舞いを1つ選ぶ。
その振る舞いを表すテストを1つだけ追加する。

Redで確認すること：

- 新しいテストが期待した理由で失敗している
- 失敗理由が、まだ実装されていない振る舞いを指している
- テストコード自体の構文エラーやセットアップ不備が原因ではない

期待と違う理由で失敗した場合は、プロダクションコードへ進まず、テストを修正してから再度Redを確認する。

### 2. Green

失敗したテストを通すために、最小限のプロダクションコードを書く。
この段階では美しい一般解を急がない。

Greenで許される実装技法：

- 仮実装: 固定値を返して最初のテストを通す
- 明白な実装: 実装が明らかな場合に、素直なコードで通す
- 三角測量: 例を追加して一般化の必要性を明らかにする

Greenで避けること：

- まだテストされていない振る舞いを先回りして実装する
- ついでに設計を大きく変える
- 複数のTODOを一度に解決する
- テストを弱めて通す

### 3. Refactor

すべてのテストがGreenになった後で、設計を整える。
Refactorでは外から見た振る舞いを変えない。

Refactorで行うこと：

- 重複を取り除く
- 名前を改善する
- 責務を分ける
- 意図が分かる構造へ並べ替える
- テストコードの読みやすさを上げる

Refactor後は必ずテストを再実行する。
テストが失敗したら、Refactorを小さく戻すか修正し、Greenへ戻してから次に進む。

## 実装技法

### 仮実装

最初の一歩が大きくなりそうなときは、固定値や単純な分岐でテストを通してよい。
仮実装は手抜きではなく、Red-Green-Refactorの歩幅を小さく保つための技法として使う。

仮実装を使ったら、TODOに一般化すべきケースを追加する。

### 三角測量

1つの例だけでは一般化の方向が危ういときは、次のRedで別の具体例を追加する。
複数の例によって、固定値では通らない状態を作ってから実装を一般化する。

### 明白な実装

実装が明らかで、仮実装や三角測量を挟む方が不自然な場合は、すぐに明白な実装を書いてよい。
ただし、必ず先に失敗するテストを書く。

## 作業手順

TDDでの実装を求められたら、以下の順番で進める。

1. 対象コードと既存テストを読む
2. 既存のテストコマンドを確認する
3. TODOリストを作る
4. 最小のTODOを1つ選ぶ
5. Red: テストを1つ追加し、失敗を確認する
6. Green: 最小限の実装でテストを通す
7. Refactor: 必要なら設計を整え、再度テストを通す
8. TODOリストを更新する
9. 目的を満たすまで 4-8 を繰り返す
10. 最後に関連テストをまとめて実行する

作業報告では、現在のサイクルが Red / Green / Refactor のどこかを明示する。

## レガシーコードへの適用

既存コードにテストがない、または安全に変更できない場合は、いきなり内部を変更しない。

1. 現在の振る舞いを観察する
2. 変更したい箇所の外側に、公開された振る舞いを押さえる characterization test を書く
3. そのテストが通ることを確認する
4. 新しい振る舞いについてRedから始める

characterization testは、現状の良し悪しを判断するためではなく、変更前の振る舞いを固定して安全に作業するために書く。

## テストが難しいとき

テストが書けない、またはテストが不自然に大きくなる場合は、設計からのフィードバックとして扱う。

- 公開APIが大きすぎないか
- 副作用と計算が混ざっていないか
- 時刻・乱数・外部APIなどの管理外依存が直接埋め込まれていないか
- 1つの関数やクラスが複数の責務を持っていないか

ただし、設計変更も必ずGreenの状態で行う。
設計変更が新しい振る舞いを必要とするなら、次のRedとして扱う。

## 禁止事項

- 「あとでテストを書く」と言って先に実装する
- テストを書かずにリファクタリングを始める
- Redを確認せずにGreenの作業へ進む
- Redの理由を確認せずにプロダクションコードを変更する
- テストを通すために仕様を曖昧にする
- 内部実装の都合をテスト名に書く
- Refactor中に機能追加する
- テスト失敗を残したまま作業完了とする

## 完了条件

TDDでの作業を完了するときは、以下を満たすこと。

- TODOリストの対象範囲が完了している、または残TODOが明確に説明されている
- 追加したテストが少なくとも一度Redになっている
- 最終的に関連テストがGreenになっている
- Refactorが必要な箇所を確認済みである
- 実装した振る舞いがテスト名から読み取れる

最終報告では、実装内容だけでなく、実行したテストコマンドと結果を必ず伝える。
