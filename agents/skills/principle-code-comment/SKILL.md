# Principle Code Comment

コードコメントに書くのは Why not である。
読み手がコードを見て「なぜもっと素直に書かないのか」「これは消してよいのでは」と思う箇所に、そうしない理由を書く。

情報には、それぞれ置くべき場所がある。

| 場所 | 書くこと |
|---|---|
| コード | How |
| テストコード | What |
| コミットログ | Why |
| コードコメント | Why not |

ほかの場所に置くべきことをコメントに書くと、読む量が増えるうえ、コードが変わったときに古くなって嘘をつく。
このスキルの方針は、この役割分担から導かれている。

## 基本方針

### 1. 原則として書かない

まず、コードと名前で意図が伝わるようにする。
コメントを書きたくなったら、先に次を検討する。

- 変数や関数の名前で意図を表せないか
- 処理を、意図を表す名前の関数に切り出せないか
- 型で制約を表せないか

### 2. Why not だけを書く

| Why not の種類 | 例 |
|---|---|
| 素直な代案を採らなかった理由 | 「Object.groupBy を使わない。対象の Node 20 には未実装で、実行時エラーになる」 |
| 外部の仕様や API の制約、既知のバグの回避策（参照先も書く） | 「数値のまま渡さない。決済 API は金額を文字列で受け取る仕様で、数値を渡すと 400 で拒否される（API 仕様書 3.2 節）」 |
| 一見不要・不自然に見えるコードを消さない理由 | 「2回目の更新は消さない。1回目の更新で発火したトリガーが updated_by を書き換えるため、2回目で正しい値に戻す」 |
| 警告やエラーを抑える理由 | 「`// @ts-expect-error` ライブラリの型定義が v3 の戻り値に追従していない（issue #123）」 |

Why not には、代案を採った場合に何が起きるか（実行時エラーになる、400 で拒否されるなど）まで書く。
どうするかを一言添えてよい（「〜のため、送る前に変換する」）。手順までは書かない。
制約を名前付きの定数や関数に切り出したら、Why not はその定義の直前に書き、使う側には重ねて書かない。

書こうとしているコメントが Why not になっておらず、5節の例外にも当たらなければ、置き場所を見直す（3節の表の「代わりに」を参照）。

### 3. 次のことは書かない

| 書かないこと | 例 | 代わりに |
|---|---|---|
| 処理の実況（How） | 「ユーザー情報を取得する」 | 関数名や変数名で表す |
| 振る舞いの仕様（What） | 「5000円以上なら送料無料」 | テスト名で表す |
| 変更の理由や履歴（Why） | 「ここを修正した」「以前は〜だった」「〜になったため」 | コミットメッセージに書く |
| 型や引数名の言い換え | 「userId: ユーザーのID」 | 書かない |
| 使われていないコードのコメントアウト | 古い実装を残す | 削除する。履歴はバージョン管理にある |

履歴かどうかは、前の状態を知らなくても読んで成り立つかで判断する。
「並列に送らない。外部 API は毎秒5件を超えると 429 を返すため」は今も成り立つ制約なので書いてよい。
「API の上限が下がったため直列に変更」は前の状態を前提にしているので書かない。

### 4. プロジェクトの言語と書き方に合わせ、短く書く

コメントの言語（日本語、英語など）は、プロジェクトの既存のコメントに合わせる。既存のコメントがなければ、README やコミットメッセージなど、プロジェクトで使われている言語に合わせる。
1文を短くし、その言語として自然な言い回しで書く。

### 5. 例外: コードやテストから What を読み取れない読み手がいる場合

What はテストに置くのが原則だが、次の2つはコメントに書いてよい。

- **密な処理の要約**: 正規表現やビット演算など、コードから意図が読み取れない処理には、何をしたいのかを書く（「日本の郵便番号（ハイフンあり・なし）に一致する」）。正規表現そのものを書き写したコメントは、要約にならない
- **公開 API のドキュメントコメント**（JSDoc、docstring など）: 引数、戻り値、例外、使い方の例を書いてよい。利用者はコードもテストも読まずに使うためである。対象は、パッケージの外やほかのチームから使われる API に限る（モジュール間の export だけでは当たらない）。型と名前を言い換えるだけのものは書かない

## 既存のコードを編集するとき

- ファイルや直接依存するモジュールのコメントに確立した書き方（JSDoc を必ず付けるなど）があれば、それに従う。新しく追加する関数にも当てはめる
- 頼まれていない限り、既存のコメントを書き換えたり消したりしない。ただし、自分の変更で内容が古くなったコメントは、変更に合わせて直すか消す
- 自分の変更で公開 API の名前と挙動がずれたときは、頼まれていない限り名前は変えない（利用者が壊れるため）。ずれをコメントや JSDoc に書き、改名の提案はユーザーへの報告に書く
- 変更の説明はコメントに書かず、コミットメッセージやプルリクエストの説明に書く

## 例

悪い例：How（処理の実況）と型の言い換えを書いている。

```ts
// ユーザーIDからユーザーを取得する
// id: ユーザーID
const getUser = async (id: UserId): Promise<User | null> => {
  // DBに問い合わせる
  const row = await db.queryOne<UserRow>("select * from users where id = $1", [id]);
  // 見つからなければnullを返す
  return row ? toUser(row) : null;
};
```

良い例：How はコードと名前に任せる。

```ts
const getUser = async (id: UserId): Promise<User | null> => {
  const row = await db.queryOne<UserRow>("select * from users where id = $1", [id]);
  return row ? toUser(row) : null;
};
```

良い例：Why not を書いている。読み手が「並列に送ればよいのでは」と思う箇所に、そうしない理由を書く。

```ts
// 並列に送らない。外部 API は毎秒5件を超えると 429 を返すため、1件ずつ間隔を空ける
for (const order of orders) {
  await sendOrder(order);
  await sleep(200);
}
```

悪い例：Why（変更の理由と履歴）を書いている。

```ts
// 以前は Math.round だったが、切り捨てに修正した
const calculatePoints = (amount: number): number => Math.floor(amount * POINT_RATE);
```

良い例：履歴はコミットメッセージに移し、今も必要な理由だけを Why not の形で書く。

```ts
// Math.round にしない。会員規約でポイントの端数は切り捨てと定められている（第5条）
const calculatePoints = (amount: number): number => Math.floor(amount * POINT_RATE);
```

読み手が代案を思い浮かべない箇所なら、コメントは書かなくてよい。

## テストコードのコメント

テストコードにも同じ方針を当てはめる。
何を検証しているかはコメントではなくテスト名で表す。テスト名は、仕様として読める文にする。

## レビューのチェックリスト

コメントのレビューを頼まれたら、次の観点で確認する。指摘ごとに、対象の行、問題、修正案（削除、名前の変更、書き直した文）を示す。

- [ ] 各コメントが Why not か、5節の例外に当たるか。どちらでもない How・What・Why は、名前・テスト名・コミットメッセージに移す修正案を示す
- [ ] 型や引数名の言い換えを書いていないか
- [ ] Why not のコメントは、代案を採った場合に何が起きるかまで伝わるか
- [ ] 読み手が「もっと素直に書けるのでは」と思う箇所に、Why not が欠けていないか
- [ ] コードと食い違ったコメントが残っていないか。食い違いは、コメントとコードのどちらが正しいかを決めつけず、仕様の確認として挙げる
- [ ] コメントアウトされたコードが残っていないか
- [ ] プロジェクトの既存のコメントと同じ言語で、短く自然な文で書かれているか
