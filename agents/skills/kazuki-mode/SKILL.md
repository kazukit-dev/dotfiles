# Kazuki Mode

kazuki がコードを書くときに意識している原則は、principle 系のスキルにまとまっている。
それぞれのスキルは単独で完結していて、ほかのスキルを参照しない。
このスキルは、作業の種類に応じてどの原則を読むかを決め、原則どうしの組み合わせ方と報告のまとめ方を定める。

## 原則の一覧

| スキル | 扱う原則 |
|---|---|
| `principle-testing` | 振る舞いを検証する、変化しないテストを書く。テストダブルは極力使わない。ユニットテストを最も多くする |
| `principle-bug-fixing` | 症状ではなく原因を直す。同じ原因を持つ箇所も直す。再現テストで捉えてから直す |
| `principle-functional-programming` | 業務のモデルを型で表し、純粋関数で状態を遷移させる。I/O は端に寄せ、依存はカリー化で注入する |
| `principle-code-comment` | コメントには Why not だけを書く。How はコード、What はテスト、Why はコミットログに置く |

## 作業ごとに読む原則

作業を始める前に、下の表で該当する原則のスキルを読み込む（Claude Code では Skill ツール、Codex ではスキルの SKILL.md を読む）。
すでに読み込まれているスキルは、読み直さなくてよい。

| 作業 | 読む原則 |
|---|---|
| 実装する（新しい処理、機能追加、仕様変更）・リファクタリングする | `principle-functional-programming`、`principle-testing`、`principle-code-comment` |
| バグを直す | `principle-bug-fixing`、`principle-testing`、`principle-code-comment` |
| テストを書く・直す | `principle-testing`、`principle-code-comment` |
| コードをレビューする | 対象に応じて上の行から選ぶ。テストコードだけなら `principle-testing`、コメントだけなら `principle-code-comment` |

`principle-functional-programming` は、対象のプロジェクトがクラスを中心に書かれている場合は関数型の書き方を持ち込まない、と自身で定めている。読み込んだうえで、その判断に従う。

## 日本語で書くとき

コードコメント、テスト名、コミットメッセージ、プルリクエストの説明、ユーザーへの報告などを日本語で書くときは、`natural-japanese` スキルを読み込み、それに従って書く。
コメントやテスト名を日本語で書くかどうかは、プロジェクトの既存の書き方で決める（`principle-code-comment` に従う）。日本語で書くと決まったら、`natural-japanese` で文を整える。
テスト名、コメント、コミットメッセージ、報告のような短い文では、`natural-japanese` の書き方の規則に従えばよい。文書を作るための工程（スクリプトによる検査など）は必須にしない。

## 原則どうしの優先順位

1. **ユーザーの明示的な指示**を最優先する
2. **プロジェクトの既存の書き方**（言語、フレームワーク、命名、テストの書き方、コメントの書き方）を、原則より優先する。原則に合わせるためだけに既存のコードを書き換えない
3. **作業の手順を定める原則**を、書き方を定める原則より優先する。バグ修正では `principle-bug-fixing` の手順で進め、テストの書き方は `principle-testing`、コメントは `principle-code-comment` に従う
4. ユーザーが TDD での開発を求めた場合は、作業の進め方は `tdd` スキルに従い、principle 系からは書き方の原則だけを使う

原則どうしが食い違って判断できないときは、どちらかを推測で選ばず、両方の案を示してユーザーに確認する。

## 報告のまとめ方

複数の原則がそれぞれ報告の形式を定めているときは、作業の手順を定める原則の形式を主にし、ほかの原則が求める項目をその中に差し込んで、1つの報告にまとめる。

| 作業 | 主にする形式 | 差し込む項目 |
|---|---|---|
| バグ修正 | `principle-bug-fixing` の「報告」 | 追加したテストのユニットとインテグレーションの別（`principle-testing`） |
| リファクタリング | `principle-functional-programming` の「リファクタリングを頼まれたとき」の4点 | 追加・実行したテストの一覧と結果（`principle-testing`） |
| 実装（新しい処理、機能追加、仕様変更） | 次の4点: 変更の要点（コードの差分か主要部分）、変更の内容と理由、呼び出し側への影響、追加したテストの一覧（ユニットとインテグレーションの別）と実行結果 | なし |
| テストを書く | `principle-testing` の報告 | なし |
| レビュー | 対象の原則のレビュー出力 | 複数の原則にまたがる場合は、原則ごとの節、全体の要約、前提と質問の順に並べる。各原則の出力にある仕様の確認点などは、最後の「前提と質問」にまとめる |

推測した前提、範囲外で見つけた不備、仕様として疑わしい点は、報告の最後に1つの節にまとめる。主にする形式に同じ役割の節（「別件と質問」など）があれば、その名前と位置を使う。なければ「前提と質問」とする。

## 作業の終わりに確かめること

- 読み込んだ各原則のチェックリスト（あれば）で、自分の変更を確認したか
- テストを実行し、結果を報告に書いたか（テストの仕組みがないプロジェクトでは、代わりに行った確認を書いたか）
- 頼まれていない範囲のコードを書き換えていないか
