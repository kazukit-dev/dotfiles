# Code Review

汎用コードレビュースキル。AI生成コードは「熱心だが経験の浅いジュニアの下書き」として扱う。コンパイルが通りテストが通っていても正しさの証明ではない。もっともらしく見えることと正しいことは別物。

## レビューの進め方

1. **変更の種類を特定し、重点観点を決める**(下表)。全観点を毎回同じ深さでなめない。重点観点は必ず、他は目についたら指摘。
2. **レビュー範囲を確定する**(次節)。diffの行だけを見て指摘しない。読んでいないコードについて断定しない。
3. **意図を確認する。** PR説明・issue・依頼内容と実装が一致しているか。説明がない変更が混ざっていないか。
4. 観点チェック → severity付きで指摘 → 出力フォーマットに従ってまとめる。

| 変更の種類 | 重点観点 |
|---|---|
| バグ修正 | B 根本原因, F テスト, A 正しさ |
| 機能追加 | A 正しさ, D 設計・スコープ, E セキュリティ, F テスト |
| リファクタ | D 設計・スコープ(挙動不変か), F テスト |
| エラー処理・耐障害性の変更 | C エラーハンドリング |
| 依存追加・更新 | G 依存, E セキュリティ |

観点0(機械チェック)は変更の種類に関わらず必ず実行する。

## レビュー範囲の定義

diffの変更行だけをレビューしない。範囲は3層で定義する。

### 一次対象(全観点を適用し、指摘する範囲)

- **変更行を含む関数・メソッドの全体。** 1行の変更でも、それを含む関数を先頭から末尾まで読み、関数全体を指摘対象とする。変更行が正しくても、同じ関数内の既存ロジックとの矛盾・不変条件の破壊はここで検出する。
- **メソッドが変更されたクラスの骨格。** フィールド定義、コンストラクタ、変更メソッドと状態を共有する他メソッド。クラスの不変条件(どのフィールドがどのメソッドで更新されるか)を把握してから変更メソッドを判定する。
- 取得方法: `git diff --function-context`(`-W`)を使うと変更行を含む関数全体がdiffに含まれる。それでも不足する場合(クラス骨格、デコレータ、関数外の定数参照)は対象ファイルを開いて読む。

### 文脈(必ず読むが、指摘は変更に関連する場合のみ)

- **変更された関数の直接の呼び出し元・呼び出し先(1ホップ)。** シグネチャ・戻り値・例外の変更が呼び出し元の前提を壊していないか。観点B(根本原因)の上流確認もここで行う。
- **変更に対応するテストファイル。** テストが変更に追随しているか、観点Fの判定に使う。
- **同じパターンを持つ別箇所。** 同種のバグ・同種の修正漏れがないかの確認(grep等で機械的に探す)。

### 対象外

- 変更と無関係な既存コードへの指摘はしない(レビューノイズになる)。
- ただし一次対象・文脈の中で**既存の問題**(変更前からあるバグ・脆弱性)を見つけた場合は、`[既存]` タグを付けて通常の指摘と区別して報告する。既存問題はこのPRのマージブロック理由にしない。例外として、高severityの脆弱性・データ破壊は既存でも即報告し対応を促す。

### 判定質問

**「この関数・このクラスを頭から読んだうえで、この変更は整合しているか」**——diffのhunkだけを見て答えたなら、範囲の確定に戻る。

## 観点0: 機械チェックの通過

レビューの最初に、プロジェクトに設定されているコマンドを実際に実行して通過を確認する。

- **lint**(例: `npm run lint`、eslint)
- **formatter**(例: prettier --check)
- **型チェック**(型付き言語なら。例: `tsc --noEmit`)
- ビルド・既存テストが短時間で走るならそれも実行する。

実行結果は次の4分岐で扱う。**失敗を高severityとして報告する前に、必ず変更前(`git stash`等)でも同じく失敗するかを確認する。** この一手順を飛ばすと、元から壊れていたlint設定やCIスクリプトをこのPRの責任として報告してしまう。

| 結果 | 扱い |
|---|---|
| 通過 | 実行したコマンドと通過を1行で報告 |
| 失敗し、変更前では通る | diff起因。高severityで報告し、マージブロックとする |
| 失敗し、変更前でも同じく失敗する | 既存・環境要因。`[既存]`タグを付けて報告し、このPRのマージブロック理由にはしない |
| コマンド自体が存在しない・実行できない環境 | 総評に明記。未実行のまま「通る」と断定しない |

severityと`[既存]`を併記するときは `[高/既存]` のようにスラッシュで繋ぐ。

これらが検出する問題(未使用変数、空のcatch、フォーマット崩れ等)を目視で探して指摘に書くことはしない——実行結果がすべて。

## 観点A: 正しさ

**既定severity: 高**(クラッシュ・データ破壊・黙って間違う失敗に至るもの)。表示崩れ程度に留まるものは中。

- **境界値**: 空配列、null/undefined、0、負数、最大値、Unicode、空文字列で何が起きるか。AIコードは典型入力では動くが境界で壊れる傾向が強い。
- **非同期の意味論**: レースコンディション(共有状態への並行書き込み、チェックと使用の間の状態変化)、Promiseの完了順序への暗黙の依存、意図的な逐次awaitか並列化すべきかの判断。awaitの位置と順序が正しいかを見る。
- **黙って間違う失敗**: 例外は出ないが結果が誤っているパス(semantic error)。型が合っていても単位・順序・符号が違う等。
- 判定質問: **「空・最大・異常な入力を入れたとき、この関数は何を返すか」**

## 観点B: 根本原因(バグ修正のとき必須)

**既定severity: 高**(症状パッチ・再現テスト欠如とも。根本原因が残る=同じバグが別経路で再発するため)

AIエージェントは最も抵抗の少ない経路を取り、バグの発生源ではなく症状が現れた場所を直しがち。

- **レイヤーの一致**: 修正箇所はバグの発生源か。呼び出し側・表示層・消費側だけを直し、呼ばれる側・生成側・シリアライズ層に触れていなければフラグ。「なぜこの値がここで壊れるのか」の説明が無ければ上流の確認を要求。
- **特殊ケースガードの追加**: `if (x === undefined) return;` 等の早期リターンや分岐の**追加**だけで解消している場合はフラグ。undefinedが来る理由の説明が無ければ症状パッチの可能性が高い。
- **再現テスト**: 修正前なら失敗するテストがdiffに含まれるか。無ければ要求する。症状パッチは根本原因レベルのテストを通せないため、これが最強の検出手段。
- 判定質問: **「この修正を取り消したら、何のテストが落ちるか」**

指摘時は却下ではなく「①潰している症状 ②根本原因の仮説(疑うべき上流) ③再現テスト→根本修正の提案」の形で返す。

## 観点C: エラーハンドリング

エラー処理は境界(エラーミドルウェア、error boundary、エントリポイント、ジョブ最上位)に集約し、中間層はthrowで伝播が原則。

**高**(必ず指摘):
- **握りつぶし**: catchがログだけ吐いて null/undefined/デフォルト値を返し継続。サイレント失敗はクラッシュより悪い(クラッシュは即直されるが、壊れたデータは残り続ける)。
- **catch-all + 継続**: 例外種別を問わず捕捉し、ログや警告を出したうえで処理を続けるもの。ログを1行足しただけで「処理済み」の形になっているものを含む。
- **エラー情報の欠落**: 元エラーを捨てて汎用メッセージだけ投げ直す。cause・ステータス・パラメータを保持させる。

**中**:
- **境界以外のcatch**: その場に具体的な回復動作(リトライ、代替パス、明確な通知)がある場合のみ許可。
- **頼まれていないフォールバック**: `|| defaultValue`、過剰な `?.`、不要なリトライ。必須値へのデフォルトは設定ミスを隠す。
- **try範囲の過大**: 例外を投げうる処理と投げない処理を一緒に囲み、どこで失敗したか分からなくするもの。

- 判定質問: **「このcatchは何から回復しているのか」**——具体的に答えられなければ削除してthrow。

## 観点D: 設計・スコープ

**既定severity: 中**(頼まれていない変更・過剰構築・既存パターンとの不整合)。公開APIの後方互換破壊は**高**。

- **頼まれていない変更**: 「ついでの」リファクタ、抽象化、ヘルパー関数、コンポーネント再構築。依頼範囲外の差分はすべてフラグし、分離を要求。
- **過剰構築**: 1回しか使わない抽象、将来のためだけの柔軟性、不要な設定オプション。
- **既存パターンとの整合**: コードベースに2つの流儀があるとき、AIは両者を「平均」した第3のパターンを作りがち。既存のどちらかに寄せる。矛盾に気づいたら指摘として表面化させる。
- **公開APIと後方互換**: シグネチャ・レスポンス形式・DBスキーマの変更は互換性影響を明示させる。

## 観点E: セキュリティ

**既定severity: 高**(注入・認可欠落・境界での検証欠落。情報漏洩は露出内容に応じて高〜中)

- **入力検証は境界で**: 外部入力(リクエスト、ファイル、環境変数)がシステム境界で検証されているか。内側での重複検証は不要、境界での欠落は高severity。
- **注入**: SQL/コマンド/パス/テンプレートへの文字列連結のうち、**連結される値が外部由来のもの**。値の出所をデータフローで追って判断する。
- **認可の欠落**: エンドポイント・操作に対する権限チェックの有無と粒度(所有者確認まであるか)。
- **エラー経由の情報漏洩**: スタックトレースや内部詳細を未フィルタでユーザー・APIレスポンスに露出していないか。

## 観点F: テスト

**既定severity: 中**(テスト欠如・無価値なassertion)。ただしバグ修正の再現テスト欠如は観点Bとして**高**。

- **バグ修正には再現テスト**(観点B)。
- **assertionの意味**: 実装をなぞるだけのテスト、モックの戻り値を検証しているだけのテストは無価値としてフラグ。壊れたら困る挙動を検証しているか。
- **境界ケースの網羅**: 観点Aの境界値がテストされているか。
- **テストを通すためのプロダクションコード変更**: テスト都合の分岐・export追加はフラグ。

## 観点G: 依存・API実在性

**既定severity: 高**(実在しないAPI・紛らわしいパッケージ名・挙動が期待と違うAPI)。非推奨APIは中。

実在しないimportは観点0で落ちる。ここでは**機械チェックをすり抜けるもの**だけを見る。

- **型がany・型定義なしで素通りする呼び出し**: 型情報のないライブラリ、動的アクセス、JSファイルでのメソッド呼び出し。実在と現行APIをドキュメント・node_modulesで確認。
- **実在するが挙動が期待と違うAPI**: 型は合うが意味が違う(similar-sounding メソッド、引数の順序・単位の取り違え)。
- **非推奨API**: deprecatedでも型は存在し、ビルドは通る。
- **紛らわしいパッケージ名**: 有名パッケージに似た別物(typosquat風)。installが成功してしまうため気づきにくい。
- 判定質問: **「このメソッドは本当にこのバージョンでこの挙動か」**——「都合が良すぎる」ユーティリティは特に疑う。

## 観点H: 可読性・スロップ

**既定severity: 低**(まとめて1項目にする)。

- **コードと重複するコメント**: 自明なコメント(`// increment i`)、実装をなぞるだけの説明。コメントは「なぜ」を書くべきで「何を」は書かない。
- **命名の質**: 冗長すぎる名前、内容と一致しない名前(処理を変えたのに名前が古いまま)。
- **既存ユーティリティの再発明**: コードベースに既にある関数と同じことをする新規実装。
- **不要な中間変数・過剰な段階分け**: 読解を助けない冗長さ。

これらは低severityでまとめて指摘し、本質的な指摘を埋もれさせない。

## severity定義

- **高**: 本番障害・データ破壊・脆弱性・サイレント失敗に直結。マージブロック。
- **中**: 将来のバグ温床、保守性の毀損、スコープ違反。修正推奨。
- **低**: スタイル・冗長さ。まとめて1項目で。

## 出力フォーマット

1. 冒頭に1-3文の総評(変更の種類、全体の妥当性、最重要指摘)。
2. 続けて観点0の実行結果を1-3行で(実行したコマンドと通過/失敗、失敗時は変更前でも再現するか)。
3. 指摘は severity降順で:
   - **[高/中/低] ファイル:行** — パターン名
     - 問題の説明(1-2文)
     - 推奨修正(具体的に:「throwに戻す」「境界の○○へ移動」「再現テストを追加」等)
4. 指摘ゼロの観点は書かない。全体で指摘ゼロなら、確認した観点を1行で明示する。
5. 不確かな指摘は断定せず「要確認」と付ける。実行・検証していない主張を検証済みのように書かない。
