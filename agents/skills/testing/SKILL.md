## テスト戦略

### テストピラミッド

テストの量と粒度はピラミッド構造を基本とする。

| 層 | 目的 | 量の目安 |
|---|---|---|
| **ユニットテスト** | ドメインロジック・純粋な計算の網羅 | 多い |
| **インテグレーションテスト** | DB等の管理依存との結合、ハッピーパス中心 | 中程度 |
| **E2E テスト** | コンポーネント間の接続確認 | 少数 |

比率を数値で固定しない。コードベースの性質に応じて調整する。ドメインロジックが厚ければユニットテストが増え、外部連携が多ければインテグレーションテストの比重が上がる。

### カバレッジの扱い

- カバレッジは**テストされていない箇所を発見する指標**として使う。カバレッジが高いことはテストの質を保証しない
- 行カバレッジよりも**分岐カバレッジ**の方が有用。条件分岐を通しているかを重視する
- カバレッジ目標を一律に設定して強制しない。数値を満たすためだけの価値のないテストが増える
- カバレッジが低い箇所は「テストが足りない可能性」を示すシグナルとして扱い、実際にテストが必要かどうかは個別に判断する

### テストを書かない判断

すべてのコードにテストが必要なわけではない。以下に該当する場合、テストを書かない（または最小限にする）選択肢を検討する。

| ケース | 理由 |
|---|---|
| **ビジネスロジックを含まない薄いラッパー** | 検証すべき振る舞いがない。インテグレーションテストで間接的にカバーされる |
| **フレームワークが保証する動作** | フレームワーク自体のテストと重複する |
| **単純な委譲のみのコード** | テストの維持コストが価値を上回る |
| **使い捨てのプロトタイプ・実験コード** | 寿命が短く、テストへの投資が回収できない |

テストを書かないと判断した場合でも、その理由をチームで共有できる状態にしておくこと。

## 共通原則

### 振る舞いを検証すること

**実装の詳細をテストすると、リファクタリング耐性が失われる。** プロダクションコードを変えずにリファクタリングしただけでテストが壊れるなら、そのテストは実装の詳細に依存している。
#### 検証対象

Good
- 戻り値
- 公開された状態変化
- 公開API経由で取得できる結果
- ドメインイベント
- 例外
- エラーメッセージ
- 副作用の結果が公開契約として見えるもの
Bad
- privateメソッドの直接検証
- 内部メソッド呼び出し回数
- ある実装方式を前提とした検証
- フレームワークの内部挙動の検証

#### ユーティリティ関数は例外的に実装寄りでもよい

ユーティリティ関数・クラスは、役割が小さく純粋であることが多いため、入力と出力の対応を厳密にテストしてよい。
ただし、それでも公開契約に基づいて検証することを優先する。

---
### モックの扱い

#### 原則

古典学派のテストを採用する。
そのため、**モックしてよいのは管理外依存のみ**とする。

依存の種類だけで一律に決めず、**自分たちが管理しているか / していないか**で判断する。

#### モックしてよいもの

- 外部API
- 他チームが所有するAPI
- 時刻取得のような外部環境依存
- ランダム生成のような不安定要素
- ネットワーク
- 外部SaaS
#### モックしないもの

- ドメインモデル
- 値オブジェクト
- 純粋関数
- 同一プロセス内の小さな協調オブジェクト
- 単なる内部ロジック
- 自分たちが管理するDB・ファイルシステム・キュー・メッセージバス

---
### DAMPを優先する

テストではDRYよりDAMPを重視する。
DAMPとは、説明的で意味のある表現を保つことを指す。

#### 目指す状態

- テスト名だけで仕様が想像できる
- テスト本文を一瞥して何を確認しているか分かる
- 期待値がその場で読める
- 前提、操作、検証が近くにある
#### 避ける状態

- 共通化しすぎて意図が見えない
- 期待値が遠くに隠れている
- 何を前提にしているかが分からない
- ヘルパー経由で意味が消える
---
### AAA パターン（Arrange-Act-Assert）

```
// Arrange: テスト対象の状態を準備する
// Act: テスト対象の操作を1つだけ実行する
// Assert: 結果を検証する
```

- **Act は1行**が理想。複数の public メソッド呼び出しが必要なら設計を疑う
- `// Arrange`, `// Act`, `// Assert` のコメントを明示的に書いてもよい

---

### テスト命名規則

**内部実装を名前に入れないこと**。実装が変わると名前も変えなければならなくなる。
また、**テスト名は仕様文として読めるようにする**。
Good:
- `注文を確定すると OrderConfirmed イベントが記録される`
- `契約終了日が開始日より前ならエラーになる`
- `税率10%のとき税込価格を返す`

Bad:
- `confirm test`
- `should work`
- `normal case`
- `can save`

## テストを書くときの行動手順

テストの実装を求められたら、以下のステップで進めること：

1. **仕様もしくは対象コードを読み、公開APIを特定する** — 戻り値・公開状態・外部への副作用を洗い出す
2. **依存を分類する** — 管理依存か管理外依存かを判断し、モック対象を決める
3. **テストの種類を判定する** — プロセス外依存を伴うテスト、または複数コンポーネントの連携を検証するテストはインテグレーションテストとして扱う。単一の振る舞いを高速かつ独立して検証できるものはユニットテストとして扱う
4. **テストスタイルを選ぶ** — 出力ベース → 状態ベース → 通信ベースの優先順で検討する
5. **テストを書く** — AAA パターンで構成し、テスト名は仕様文として読めるようにする
6. **セルフレビュー** — 実装の詳細に依存していないか、リファクタリングしてもテストが壊れないかを確認する

## テストコードのレビューチェックリスト

テストコードのレビューを求められたら、以下の観点で確認すること。

### 設計

- [ ] テストが振る舞い（公開API・戻り値・状態変化・副作用）を検証しているか。実装の詳細（privateメソッド・内部呼び出し回数）に依存していないか
- [ ] モック対象が管理外依存に限定されているか。管理依存（自チームのDB等）をモックしていないか
- [ ] テストスタイルの選択は妥当か（出力ベース → 状態ベース → 通信ベースの優先順）
- [ ] テストの種類（ユニット / インテグレーション）が適切か。ユニットテストにプロセス外依存が混入していないか

### 可読性

- [ ] テスト名だけで仕様が読み取れるか。`should work` や `normal case` のような曖昧な名前になっていないか
- [ ] AAA パターン（Arrange-Act-Assert）で構成されているか。Act は1操作に絞られているか
- [ ] 期待値・前提条件がテスト本文に明示されているか。離れたヘルパーや setUp に隠れていないか
- [ ] DAMP を満たしているか。過度な共通化で意図が見えなくなっていないか

### テストケースの網羅性

- [ ] 正常系のハッピーパスがカバーされているか
- [ ] 境界値（0, 1, 上限, 空, null）が検証されているか
- [ ] 異常系・エラーケース（不正入力、依存の失敗）が検証されているか
- [ ] ユニットテストでエッジケースを十分に網羅し、インテグレーションテストとの重複を避けているか

### 保守性・実行品質

- [ ] テスト間で状態を共有していないか。任意の順序・並列で実行できるか
- [ ] テストが遅くないか。不要なI/O・sleep・大きなデータセットを含んでいないか
- [ ] リファクタリング耐性があるか。プロダクションコードの内部構造を変えただけでテストが壊れないか
- [ ] フレイキー（不安定）な要素がないか。時刻・乱数・ネットワークなどの不確定要素が適切に制御されているか
