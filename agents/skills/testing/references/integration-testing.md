# インテグレーションテストの書き方・設計

---

## インテグレーションテストの定義

以下のいずれかに該当するテスト：

- **プロセス外依存（out-of-process dependency）** を伴う
  - データベース、ファイルシステム、メッセージブローカー、外部APIなど
- **複数コンポーネントの連携**を検証する

> ユニットテストと同じく「実行が速い・独立している」は重要だが、外部依存があるため完全な速度は求めない。

---

## 依存の2分類（最重要）

インテグレーションテストの設計はこの分類で決まる。

### 管理依存（Managed dependency）

自分たちのチームが**完全にコントロール**できる依存。  
外のシステムからは直接見えない（実装の詳細）。

| 例 | 方針 |
|----|------|
| 自分たちのデータベース | **実物を使う**（テスト用DB） |
| ファイルシステム | **実物を使う** |
| 自分たちが管理するメッセージキュー | **実物を使う** |

### 管理外依存（Unmanaged dependency）

自分たちがコントロールできない依存。  
外のシステムが直接観測する（可観測な振る舞い）。

| 例 | 方針 |
|----|------|
| 外部メールAPI（SendGrid など） | **Mock する** |
| 外部決済サービス（Stripe など） | **Mock する** |
| 他チームが所有するAPI | **Mock する** |
| SMTPサーバー | **Mock する** |

> **管理依存をモックにするのは誤り**。テストのために余計な層（リポジトリのインターフェース）を作り、実装詳細を検証することになる。  
> 管理外依存をモックにしないのも誤り。本番の外部サービスへの副作用が発生する。

## インテグレーションテストの書き方

### 基本テンプレート

```csharp
[Fact]
public void PurchaseSuccessfully_WithEnoughInventory()
{
    // Arrange
    var db = new TestDatabase();               // 実物のテスト用DB
    var emailGateway = new Mock<IEmailGateway>(); // 管理外依存はMock
    var sut = new PurchaseService(db, emailGateway.Object);

    db.Products.Add(new Product("Book", stock: 10));
    db.SaveChanges();

    // Act
    sut.Purchase(customerId: 1, productId: "Book", quantity: 2);

    // Assert
    // 状態の検証（DB）
    var product = db.Products.Find("Book");
    product.Stock.Should().Be(8);

    // 外部への副作用の検証（Mock）
    emailGateway.Verify(e => e.Send(
        It.Is<Email>(m => m.Subject == "Purchase confirmed")));
}
```

### テスト用DBのセットアップ方針

| 方針                  | 説明                                        |
| ------------------- | ----------------------------------------- |
| **テストごとにクリーンな状態**   | 理想はテストケースが実行された一番初めにデータのクリーンアップ＆テストデータの用意 |
| **本番DBとスキーマを同一に保つ** | マイグレーションスクリプトをテスト環境にも適用                   |
| **テストデータは明示的に作る**   | 共有フィクスチャに頼らない                             |

## インテグレーションテストでチェックする観点

| 観点             | 何を確認するか               |
| -------------- | --------------------- |
| **正常系の状態変化**   | DBに正しいデータが書き込まれるか     |
| **管理外依存への副作用** | 外部サービスへ正しいメッセージが送られるか |
| **ハッピーパス1つ**   | 最も重要なユースケースが通るか       |
| **エラーケース**     | 外部依存の失敗を適切にハンドリングするか  |

> **インテグレーションテストはハッピーパスを中心に書く。** エッジケースはユニットテストで網羅済みのため、インテグレーションテストで重複して書く必要はない。

## よくある設計の問題と対策

### ❌ サービス全体をモックにしてインテグレーションテストと呼ぶ

各レイヤーをすべてモックにすると、実際の結合を検証していない。  
インテグレーションテストの価値は「本物の依存との結合を検証すること」にある。

---

## E2E テストの位置付け

E2E テストは**ユーザー視点での最終確認**として少数用意する。

- API のエンドポイント（HTTP リクエスト）から始める
- 本物のDB・本物のファイルシステムを使う
- 管理外依存（外部API）のみMock
- **実行コストが高いため、カバー範囲は絞る**

```
E2E で確認するのは「コンポーネント間の接続が正しいか」のみ。
ビジネスロジックはユニットテストで。
インフラとの結合はインテグレーションテストで。
```

## アンチパターン一覧

| アンチパターン                     | 問題             | 対策              |
| --------------------------- | -------------- | --------------- |
| **管理依存のモック**                | DBのバグを見逃す      | テスト用DBを実物で使う    |
| **テスト間でDBデータを共有**           | テスト順序依存        | テストごとにデータ初期化    |
| **インテグレーションテストでエッジケースを全網羅** | 遅い・重複する        | エッジケースはユニットテストへ |
| **E2Eテストだけに頼る**             | 遅い・失敗原因が特定しにくい | ピラミッド構造を守る      |
| **外部APIを本番で叩く**             | 副作用・コスト・不安定    | 管理外依存はMockする    |
