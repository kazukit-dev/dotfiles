# ユニットテストの書き方・設計

---

## ユニットテストの定義

1. **少量のコード（unit）を検証する**
2. **実行が速い**
3. **他のテストから隔離されている**（並列実行・任意の順序で実行できる）

> **「unit」= クラス1つ、ではない。** 振る舞いのひとかたまり（a unit of behavior）が unit。複数のクラスにまたがっていても構わない。

---
## テストスタイルの3分類

| スタイル | 検証するもの | リファクタリング耐性 | 退行保護 | 適用場面 |
|---------|------------|-------------------|---------|--------|
| **出力ベース（Output-based）** | 戻り値 | ◎ 高い | ◎ 高い | 副作用のない純粋関数 |
| **状態ベース（State-based）** | 操作後のオブジェクト状態 | ○ 中 | ○ 中 | ドメインオブジェクト |
| **通信ベース（Communication-based）** | 他オブジェクトへのメッセージ | △ 低い | △ 低い | 外部依存への副作用確認 |

> **出力ベースを最優先**。副作用を極力なくし、純粋な計算を増やすことでテストしやすくなる。  
> 通信ベース（モックによる検証）は**外部に出ていく副作用**の確認にのみ使う。

---

## テストダブルの種類と使い分け

### 定義

| 種類 | 役割 |
|------|------|
| **Stub** | テスト対象への入力を制御する。戻り値を偽装する |
| **Mock** | テスト対象から外部への出力を検証する |
| **Spy** | Mock の手書き実装 |
| **Fake** | 動作する簡易実装（インメモリDBなど） |
| **Dummy** | 使われない引数の穴埋め |

### 核心ルール

```
モックを使ってよいのは「管理外依存」のみ
```

| 依存の種類 | 例 | テストダブル |
|-----------|-----|-------------|
| **管理依存（Managed dependency）** | 自分たちが所有するDB、ファイルシステム | 使わない（実物または Fake を使う） |
| **管理外依存（Unmanaged dependency）** | 外部メール API、外部決済サービス、他チームのAPI | Mock で検証する |

> **管理依存をモックにすると、実装の詳細を検証することになりリファクタリング耐性が下がる。**  
> 自分たちのDBはスキーマを変えても外の世界には影響しないので、実物（テスト用DB）を使うべき。

## テストの構造設計

### 1テスト1アサーションが理想（ただし絶対ではない）

複数のアサーションが必要な場合、それは：
- 複数の振る舞いを1テストで検証しようとしている → テストを分割する
- または、1つの振る舞いの複数側面を検証している → まとめて問題ない

### テストフィクスチャ（setUp）の使い方

```
// 推奨：共通のコンテキスト準備には Factory メソッドを使う
var sut = CreateDefaultUser();

// 非推奨：すべてのテストが共有する mutable な state を setUp に書く
// → テスト間の依存が生まれる
```

- `[SetUp]` / `beforeEach` に書いてよいのは**コスト削減のための共通初期化のみ**
- テストが何をしているか読むだけでわかるよう、**重要なコンテキストはテスト本体に書く**

## テスト対象のリファクタリング方針（Humble Object パターン）

テストしにくいコードは設計の問題を示している。  
Khorikov は「**ビジネスロジックとオーケストレーションを分離**」を推奨する：

```
┌──────────────────────────────┐
│  Orchestrator（Service）      │  ← インテグレーションテストで検証
│  - 外部依存を呼ぶ             │
│  - 結果をつなぐ               │
└──────────────┬───────────────┘
               │ calls
┌──────────────▼───────────────┐
│  Domain Model                │  ← ユニットテストで検証
│  - 純粋な計算                 │
│  - 副作用なし                 │
└──────────────────────────────┘
```

- **Domain Model（ドメインオブジェクト）**：外部依存ゼロ → 出力ベースのユニットテスト
- **Orchestrator（サービス層）**：ドメインを呼び出し、DBや外部APIと繋ぐ → インテグレーションテスト

## アンチパターン一覧

| アンチパターン                | 問題           | 対策             |
| ---------------------- | ------------ | -------------- |
| **実装の詳細のテスト**          | リファクタリング耐性ゼロ | 可観測な振る舞いのみテスト  |
| **過剰なモック**             | 偽陽性・実装依存     | 管理外依存のみモック     |
| **テスト間の共有状態**          | 実行順序依存・脆いテスト | テストごとに状態をリセット  |
| **テストロジックの重複排除しすぎ**    | 読みにくい        | 適度な重複は許容する     |
| **テストがテストを呼ぶ**         | 依存連鎖         | 各テストは独立して完結させる |
| **プロダクションコードへのテスト用分岐** | 設計の臭い        | テスタビリティは設計で解決  |
