# テストダブル

テストダブルは極力使わない。
この方針は、古典学派の単体テスト（『単体テストの考え方/使い方』）と、『Software Engineering at Google』13章「Test Doubles」に基づく。

## なぜテストダブルを避けるのか

テストダブルを使うと、テストは「依存がこう振る舞うはずだ」という前提の上に成り立つ。
この前提には2つの問題がある。

- **本物とずれる。** 本物の依存の振る舞いが変わっても、テストダブルは古いままなので、テストは通り続ける。実際には壊れているのにテストが成功する
- **実装の詳細を固定する。** スタブやインタラクションテストは、対象が依存を「どう使うか」をテストに書き込む。依存の使い方を変えるリファクタリングをすると、振る舞いが同じでもテストが壊れる

どちらも、テストの目的である「変更しても振る舞いが壊れていないと確信できること」を損なう。
テストダブルが多いテストは、もろいテストである可能性が高い。

## 用語

| 種類 | 意味 | 方針 |
|---|---|---|
| 本物の実装 | 本番と同じ実装 | 最優先で使う |
| フェイク | 本番では使えないが、本物と同じように振る舞う軽量な実装（インメモリのストレージなど） | 社内サービスの開発者が用意したものがある場合だけ使う。自分たちでは書かない |
| モック | 呼び出されたときの応答をテストで指定したり（スタブ）、呼び出しを記録して検証したりするもの | 外部SaaSなど、管理外の依存の境界でだけ使う |
| インタラクションテスト | モックへの呼び出し（引数・回数）を検証するテスト | 極力避ける。条件は後述 |

## テストダブルを使ってよい条件

本物の実装を使うことを基本とし、次のどれかに当てはまるときに限ってテストダブルを検討する。

| 条件 | 例 |
|---|---|
| **実行が遅い** | 外部ネットワークを経由する呼び出し |
| **結果が安定しない** | 他チームが運用するAPI、外部SaaS、レート制限のあるサービス |
| **テスト環境で使えない** | 実際に課金・メール送信・通知が発生する外部サービス |

依存を「自分たちが管理しているか」でも判断する。

- **管理下の依存**（自分たちのアプリケーションだけが使う DB、ファイルシステム、キューなど）は、本物を使う。Docker などで立ててインテグレーションテストで検証する（[unit-and-integration.md](unit-and-integration.md) を参照）。DB の中身は外から観察されない実装の詳細であり、モックするとリファクタリングへの耐性が失われる
- **管理外の依存**（外部API、外部SaaS、他チームのサービス）は、上の条件に当てはまればテストダブルを使ってよい。何を使うかは次の節に従う

自分たちが書いたモジュール、ドメインモデル、純粋な関数は、どんな場合もテストダブルにしない。

時刻と乱数は、テストダブルではなく、値を引数で受け取る設計で制御する（[test-design.md](test-design.md) の「時刻・乱数の扱い」を参照）。

## 管理外の依存に何を使うか

| 依存 | 使うもの |
|---|---|
| 社内の他チームのサービスで、開発者がフェイクを用意している | そのフェイク |
| 上記以外（外部SaaS、フェイクのない社内サービス） | モック |

### フェイクは自分たちで書かない

フェイクは本物と同じ振る舞いを保ち続ける必要がある。
外部SaaSの仕様が変わるたびに自分たちのフェイクを追従させるのはメンテナンスの負担が大きく、追従が遅れれば本物とずれたフェイクの上でテストが通り続ける。
フェイクを使うのは、そのサービスの開発者が本物と一緒に保守しているものがある場合に限る。

### モックの使い方

外部SaaSなどをモックするときは、次を守る。

- **モックするのはシステムの境界を越える依存だけにする。** アプリケーション内部のモジュール同士の呼び出しは、どんな場合もモックしない
- **応答（スタブ）は、検証に関係する値をテストケース内で指定する。** 成功・拒否・通信エラーなど、テストの前提となる応答を共通のセットアップに隠さない（[damp.md](damp.md) を参照）
- **呼び出しの検証は、次の節の条件に当たる場合に限る。** 応答を返させるためだけにモックを使うなら、呼び出しは検証しない
- **ロジックを I/O から切り離し、モックが必要なテストを減らす。** モックを使うのは、外部SaaSとつながる外側の層のテストだけにする（「テストダブルを減らす設計」を参照）

## インタラクションテストを使う条件

インタラクションテストは極力避ける。
呼び出しを検証したくなったら、次の順で置き換えられないかを考える。

1. **出力値ベーステストにできないか。** 呼び出しの結果が戻り値に表れるなら、戻り値を検証する
2. **状態ベーステストにできないか。** 公開インターフェースから取得できる状態や、社内サービスの開発者が用意したフェイクの状態で検証する
3. **インテグレーションテストにできないか。** 管理下の依存であれば、本物を立てて結果を検証する。DBへのクエリ回数のように回数そのものが仕様であっても、本物のDBのクエリログやメトリクスで確かめられるなら、そちらを選ぶ
4. **どれも無理なら、インタラクションテストを使う。**

4に当たるのは次のような場合である。

- **管理外の依存への副作用そのものが仕様である。** 外部のメール配信SaaSでメールを送る、決済SaaSで課金する、など。システムの外から観察できる振る舞いなので、実装の詳細ではない
- **呼び出しを抑えることが主な機能である。** キャッシュ（同じ要求では外部APIを2回呼ばない）、重複排除・バッチ化、レート制限・リトライの上限など。戻り値はその機能があってもなくても同じなので、呼び出しを検証するしかない

インタラクションテストを使う場合も、次を守る。

- **検証するのは仕様に当たる部分だけにする。** 「誰に、どのメールを送ったか」「何回呼んだか」など仕様に当たる部分だけを検証し、仕様でない引数の細部や呼び出し順序は検証しない
- **出力値や状態で検証できる振る舞いは、別のテストで検証する。**

### 副作用が仕様である例

悪い例：仕様ではない引数の細部まで検証している。

```ts
test("注文を確定すると購入者に確認メールを送る", async () => {
  const mailer = { send: mock.fn(async () => {}) };

  await confirmOrder({ orderId: "order-1", buyerEmail: "buyer@example.com" }, { mailer });

  assert.deepEqual(mailer.send.mock.calls[0].arguments, [
    {
      to: "buyer@example.com",
      template: "order-confirmed",
      subject: "【ご注文確認】order-1",
      headers: { "X-Priority": "3" },
    },
  ]);
});
```

良い例：仕様である「誰に、どのメールを送ったか」だけを検証している。

```ts
test("注文を確定すると購入者に確認メールを送る", async () => {
  const mailer = { send: mock.fn(async () => {}) };

  await confirmOrder({ orderId: "order-1", buyerEmail: "buyer@example.com" }, { mailer });

  const [mail] = mailer.send.mock.calls[0].arguments;
  assert.equal(mailer.send.mock.callCount(), 1);
  assert.equal(mail.to, "buyer@example.com");
  assert.equal(mail.template, "order-confirmed");
});
```

悪い例は、件名の文言やヘッダーの組み立て方を変えるだけで壊れる。
良い例は、仕様が変わらない限り壊れない。

### 呼び出しを抑えることが主な機能である例

キャッシュの主な機能は「外部APIへの問い合わせを減らすこと」であり、戻り値はキャッシュがあってもなくても同じになる。
そのため、外部APIの呼び出し回数を検証するしかない。

```ts
test("同じ商品の価格を続けて取得しても外部APIへの問い合わせは1回だけ", async () => {
  const fetchPriceFromApi = mock.fn(async () => 1000);
  const getPrice = createCachedPriceFetcher(fetchPriceFromApi);

  await getPrice("item-1");
  await getPrice("item-1");

  assert.equal(fetchPriceFromApi.mock.callCount(), 1);
});
```

この例では回数だけを検証する。「キャッシュから返した価格が正しい」ことは、別の出力値ベーステストで検証する。

## もろいテストの兆候

次のどれかに当てはまるテストは、実装の詳細に依存している可能性が高い。
本物の実装に置き換えられないか、出力値ベーステストや状態ベーステストに書き直せないかを検討する。

- 1つのテストで複数のテストダブルを使っている
- スタブの設定がテスト本文の大半を占めている
- 自分たちのモジュールや管理下の依存をモックしている
- 自分たちで書いたフェイクを使っている
- 呼び出し回数や呼び出し順序を検証している（インタラクションテストを使う条件に当たる場合を除く）
- スタブが返した値を、そのまま検証している（テストダブルの動作をテストしている）
- 対象の内部実装を読まないと、スタブの設定内容が理解できない

## テストダブルを減らす設計

テストダブルが必要に見えるとき、多くの場合は設計で解決できる。

- **ロジックと I/O を分ける。** 依存から値を取得する処理と、その値を使って判断する処理を分ける。判断する処理は純粋な関数になり、テストダブルなしの出力値ベーステストで検証できる
- **I/O を呼び出し側に寄せる。** 取得・保存は外側の薄い層で行い、ドメインロジックには値だけを渡す。外側の層はインテグレーションテストで検証する
- **依存を引数で受け取る。** 管理外の依存をどうしても使う場合は、引数で渡せる形にし、テストではモックを渡す

悪い例：判断のロジックが外部APIの呼び出しと混ざっているため、スタブが必要になる。

```ts
const canShip = async (orderId: string, inventoryApi: InventoryApi): Promise<boolean> => {
  const stock = await inventoryApi.getStock(orderId);
  return stock.quantity > 0 && !stock.reserved;
};
```

良い例：判断のロジックを純粋な関数に切り出すと、値を渡すだけでテストできる。

```ts
const canShip = (stock: Stock): boolean => stock.quantity > 0 && !stock.reserved;

test("在庫があり予約されていなければ出荷できる", () => {
  const result = canShip({ quantity: 3, reserved: false });

  assert.equal(result, true);
});
```
