## 良いテストの4つの性質

『単体テストの考え方/使い方』は、テストの価値を次の4つの性質で測る。

| 性質 | 意味 |
|---|---|
| 退行に対する保護 | バグが入ったときに検出できる |
| リファクタリングへの耐性 | 振る舞いを変えない変更で失敗しない |
| 迅速なフィードバック | 速く実行できる |
| 保守のしやすさ | 読みやすく、動かしやすい |

このうちリファクタリングへの耐性は、あるかないかの二択に近く、妥協できない。
一度でも誤検知（振る舞いは正しいのに失敗すること）を起こすテストは、開発者に「テストの失敗は無視してよい」と学ばせてしまう。
迷ったときは、リファクタリングへの耐性を最優先にする。

## 検証する対象

| 検証してよい | 検証しない |
|---|---|
| 戻り値 | private な関数の直接呼び出し |
| 公開インターフェースから取得できる状態 | 内部の関数の呼び出し回数・順序 |
| 例外とエラーの内容 | 特定の実装方式を前提とした中間状態 |
| 依存の呼び出し回数（それが主な機能で、他の方法では検証できない場合） | フレームワークやライブラリ自体の挙動 |

private な関数をテストしたくなったら、それは公開インターフェース経由で十分に検証できていないか、別のモジュールに切り出すべき責務が埋もれているかのどちらかである。
テストのために公開範囲を広げるのではなく、設計を見直す。

一方、I/O と混ざっていたドメインロジックを独立した関数やモジュールとして切り出し、公開するのは設計の改善であり、テストのための公開には当たらない。
見分け方は「テストがなくても、その関数は独立した責務として意味を持つか」である。
意味を持つなら切り出して公開してよい。持たないなら、公開インターフェース経由で検証する。

## テストスタイルの優先順位

次の順で検討する。上ほどリファクタリングへの耐性が高く、保守しやすい。

1. **出力値ベーステスト**: 入力を渡し、戻り値だけを検証する。副作用のない関数に使える
2. **状態ベーステスト**: 操作のあとに、公開インターフェースから状態を取得して検証する
3. **インタラクションテスト**（同書ではコミュニケーション・ベース・テスト）: 依存への呼び出しを検証する。極力避け、出力値ベーステスト・状態ベーステスト・インテグレーションテストのどれでも検証できない場合に限る（[test-doubles.md](test-doubles.md) を参照）

出力値ベーステストで書ける範囲を広げるには、ロジックを純粋な関数として切り出し、I/O を呼び出し側に寄せる。

## 振る舞いごとにテストを書く

メソッドや関数ごとに1つのテストを書くのではなく、振る舞いごとにテストを書く。
1つの関数が複数の振る舞いを持つことも、1つの振る舞いが複数の関数にまたがることもある。

悪い例：関数単位で、複数の振る舞いを1つのテストに詰め込んでいる。

```ts
test("withdraw", () => {
  const account = openAccount({ balance: 1000 });
  assert.equal(withdraw(account, 300).balance, 700);
  assert.throws(() => withdraw(account, 2000), InsufficientFundsError);
});
```

良い例：振る舞いごとに分けている。

```ts
test("残高の範囲内なら引き出した分だけ残高が減る", () => {
  const account = openAccount({ balance: 1000 });

  const result = withdraw(account, 300);

  assert.equal(result.balance, 700);
});

test("残高を超える額は引き出せない", () => {
  const account = openAccount({ balance: 1000 });

  assert.throws(() => withdraw(account, 2000), InsufficientFundsError);
});
```

振る舞いごとに分けると、失敗したテストの名前だけで、どの仕様が壊れたかが分かる。

## テストの構造（Arrange-Act-Assert）

テストは準備（Arrange）、実行（Act）、検証（Assert）の3つに分け、空行で区切る。
既存のテストファイルに追加するときは、そのファイルのスタイル（1行で書く、など）を優先する。

- **Act は1つの操作にする。** 複数の操作が必要なら、公開インターフェースの設計が不十分か、テストが複数の振る舞いを検証している
- **Act と Assert を交互に繰り返さない。** 「操作 → 検証 → 操作 → 検証」となるなら、テストを分ける
- インテグレーションテストで前提状態を作るための操作は Arrange に含める。検証対象の操作と準備の操作を区別する

例外が起きたあとの状態を確かめるテストでは、Act で `assert.rejects` を使って例外の発生を確かめ、Assert で状態を読み取る。
`.catch(() => {})` で例外を握りつぶすと、例外が起きなかった場合にも気づけない。

```ts
test("決済SaaSが通信エラーのとき注文は未決済のまま残る", async () => {
  await createOrder(db, { id: "order-1", total: 3000 });
  const paymentGateway = { charge: mock.fn(async () => { throw new PaymentGatewayError("timeout"); }) };

  await assert.rejects(checkout({ db, paymentGateway }, "order-1"), PaymentGatewayError);

  assert.equal((await findOrder(db, "order-1"))?.status, "pending");
});
```

## テスト名

テスト名は、そのテストが検証する仕様を表す文にする。
テストが失敗したとき、最初に目にするのはテスト名である。

- 関数名やメソッド名を入れない。実装が変わると名前も変える必要が出る
- 「〜すべき」「正常系」「動作する」のような曖昧な表現を使わない
- 条件と結果を書く。Given-When-Then の形が書きやすい

| 良い例 | 悪い例 |
|---|---|
| 契約終了日が開始日より前なら作成できない | `validate test` |
| 税率10%のとき税込価格を返す | 正常系 |
| 在庫が0の商品はカートに追加できない | `addToCart should work` |

テスト名に「と」「かつ」が入るなら、複数の振る舞いを検証していないかを確認する。

## テストにロジックを書かない

テストの中に分岐、ループ、文字列の組み立て、計算を書かない。
テストのロジックにもバグは入りうるが、テストのテストは書かない。
テストは、読めば正しいと分かるほど単純であるべきである。

悪い例：期待値を実装と同じ計算で求めている。

```ts
test("税込価格を返す", () => {
  const price = 1000;
  const taxRate = 0.1;

  assert.equal(calculatePriceWithTax(price, taxRate), price * (1 + taxRate));
});
```

良い例：期待値をリテラルで書いている。

```ts
test("税率10%のとき税込価格を返す", () => {
  const result = calculatePriceWithTax(1000, 0.1);

  assert.equal(result, 1100);
});
```

期待値を実装と同じ方法で計算すると、実装のバグがそのままテストにも入り、テストが通ってしまう。

複数の入力で同じ振る舞いを検証したいときは、パラメータ化テストを使ってよい。
ただし、入力と期待値の組をリテラルで並べ、1つの振る舞いに限ること。
期待値が条件によって異なる振る舞いを1つのパラメータ化テストにまとめない。

## 失敗メッセージ

テストが失敗したとき、テストコードを読まなくても何が壊れたのかが分かるようにする。

- 真偽値ではなく値そのものを比較する。`assert.ok(result === 1100)` ではなく `assert.equal(result, 1100)` と書くと、実際の値がメッセージに出る
- オブジェクトや配列は、要素ごとの比較ではなく構造ごと比較する（`assert.deepEqual`）。差分がそのまま表示される
- 1つのテストに検証が複数ある場合も、同じ振る舞いの別の側面を確かめるものに限る

## 時刻・乱数の扱い

時刻や乱数に依存するコードは、値を引数で受け取る形にし、テストでは固定値を渡す。
モックで差し替えるのではなく、依存を外から渡せる設計にする。

悪い例：現在時刻を内部で取得しているため、テストの結果が実行時刻で変わる。

```ts
const isExpired = (coupon: Coupon): boolean => coupon.expiresAt < new Date();
```

良い例：現在時刻を引数で受け取るため、テストで固定値を渡せる。

```ts
const isExpired = (coupon: Coupon, now: Date): boolean => coupon.expiresAt < now;

test("有効期限を過ぎたクーポンは期限切れになる", () => {
  const coupon = createCoupon({ expiresAt: new Date("2026-01-31T23:59:59Z") });

  const result = isExpired(coupon, new Date("2026-02-01T00:00:00Z"));

  assert.equal(result, true);
});
```

## 仕様をテストで表す

型や名前で表せない仕様は、テストケースとして書く。
コメントやドキュメントは実装とずれても気づけないが、テストはずれた時点で失敗する。

テストで表すとよい仕様の例:

- 境界値の扱い（「以上」か「より大きい」か）
- 空の入力や0件のときの振る舞い
- 結果の並び順が保証されるかどうか
- エラーになる条件と、そのときのエラーの種類
- バグ修正で明らかになった、見落としやすい条件
