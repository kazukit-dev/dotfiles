## ユニットテストの定義

古典学派（『単体テストの考え方/使い方』）の定義に従い、次の3条件をすべて満たすものをユニットテストとする。

1. **1単位の振る舞いを検証する。** 1つの関数やモジュールではなく、1つの振る舞いが単位である。振る舞いの実現に複数のモジュールが関わっても、それらを本物のまま使ってよい
2. **実行が速い。** 開発中に何度も実行できる速さで終わる
3. **他のテストから隔離されている。** 実行順序や並列実行に関係なく、毎回同じ結果になる。テストどうしが状態を共有しない

隔離するのはテストどうしであって、対象のモジュールと依存の間ではない。
ロンドン学派のように協調するモジュールをモックで切り離すことはしない。

3条件のどれか1つでも満たさないテストは、インテグレーションテストとして扱う。
DB、ファイルシステム、ネットワークなどプロセス外の依存を使うテストは、通常は2と3を満たさないため、インテグレーションテストになる。

『Software Engineering at Google』のテストサイズで言えば、ユニットテストは Small（単一プロセス、I/O なし）に当たる。

## テストの配分

ユニットテストの割合が、他のどの種類よりも多くなるように設計する。

| 種類 | 検証するもの | 量 |
|---|---|---|
| ユニットテスト | ドメインロジック、計算、判断の分岐と境界値。ビジネス上の異常系をできるだけ多く | 最も多い |
| インテグレーションテスト | 依存との結合。業務シナリオごとに最も長いハッピーパス1件と、ユニットテストでは検証できない異常系のすべて | 中程度 |
| E2E テスト | システム全体がつながって動くこと | 少数 |

ユニットテストを多くするのは、速く、安定していて、失敗した箇所の特定が容易だからである。
インテグレーションテストは信頼性が高い一方、遅く、準備のコストも大きい。
ロジックの分岐の網羅はユニットテストで行い、インテグレーションテストでは繰り返さない。

ビジネス上の異常系（不正な入力、業務ルール違反、上限超過、状態として許されない操作など）は、仕様の中でも見落とされやすく、バグが入りやすい。
ユニットテストなら速く安価に書けるので、思いつく限り多く検証する。

比率は数値で固定しない。
ただし、インテグレーションテストのほうが多くなっているなら、ロジックが I/O と混ざっていてユニットテストで検証できない設計になっていないかを疑う。

## ユニットテストの割合を増やす設計

ユニットテストを増やせるかどうかは、テストの書き方より設計で決まる。

- **ロジックと I/O を分ける。** 判断や計算は I/O を持たない純粋な関数にし、ユニットテストで検証する
- **I/O を外側の薄い層に寄せる。** 取得・保存・外部呼び出しは、ロジックをほとんど持たない層にまとめる。この層はインテグレーションテストで検証する
- **外側の層には判断を書かない。** 外側の層に分岐が増えると、その分岐をインテグレーションテストで網羅する必要が出て、テストが遅く重くなる

```ts
// ドメインロジック：純粋な関数なので、ユニットテストで網羅できる
const applyPoints = (member: Member, purchase: Purchase): Member => ({
  ...member,
  points: member.points + Math.floor(purchase.amount / 100),
});

// 外側の層：取得、ロジックの呼び出し、保存だけを行う。インテグレーションテストで検証する
const recordPurchase = async (db: Db, memberId: string, purchase: Purchase): Promise<void> => {
  const member = await findMember(db, memberId);
  await saveMember(db, applyPoints(member, purchase));
};
```

### 判定は値を返す純粋関数にする

業務ルールによる判定（受け付けてよいか、上限を超えていないか、など）は、例外を投げる関数ではなく、値（真偽値や却下の理由）を返す純粋関数として切り出す。
値を返す関数なら、出力値ベーステストで境界値まで簡潔に検証できる。

ルールが複数あるときは、ルールごとの述語と、それらを組み合わせて理由を返す関数を用意する。
判定の順序（どのルールを優先するか）も組み合わせる関数に含めると、ユニットテストで検証できる。
外側の層は、組み合わせる関数を1回呼び、その結果を例外や I/O に変換するだけにする。

```ts
const isPendingOrder = (order: Order): boolean => order.status === "pending";
const isValidAmount = (order: Order): boolean => order.total > 0;
const isWithinAmountLimit = (order: Order): boolean => order.total <= 1_000_000;

type CheckoutRejection = "not_pending" | "invalid_amount" | "limit_exceeded";

const findCheckoutRejection = (order: Order): CheckoutRejection | null => {
  if (!isPendingOrder(order)) return "not_pending";
  if (!isValidAmount(order)) return "invalid_amount";
  if (!isWithinAmountLimit(order)) return "limit_exceeded";
  return null;
};

test("上限ちょうどの金額の注文は決済を受け付ける", () => {
  const result = findCheckoutRejection({ id: "order-1", status: "pending", total: 1_000_000 });

  assert.equal(result, null);
});

test("上限を1円でも超える注文は上限超過として決済を受け付けない", () => {
  const result = findCheckoutRejection({ id: "order-1", status: "pending", total: 1_000_001 });

  assert.equal(result, "limit_exceeded");
});
```

ユニットテストは組み合わせる関数に対して書き、各ルールの境界値と判定の順序を網羅する。
述語を個別にテストするのは、中身が複雑なものに限る。
1行で済む述語を単独でテストしても、守れるものはほとんどない。

## インテグレーションテストで検証すること

インテグレーションテストでは、ロジックの細部ではなく、依存とつながったときに正しく動くことを確かめる。

- **最も長いハッピーパス。** 業務シナリオ（ユースケース）ごとに、依存をすべて通る最も長いハッピーパスを1件検証する。ハッピーパスを何通りも書くと、ユニットテストと検証内容が重なり、遅いテストが増えるだけになる。戻り値と保存結果のように、仕様として別々に述べられる結果があるときは、テストを分ける（テスト名に「と」が入るなら分ける目安になる）
- **ユニットテストでは検証できない異常系のすべて。** 一意制約違反、トランザクションの巻き戻し、依存からのエラー応答、対象が存在しない場合など、本物の依存がないと再現できない異常系は、間引かずにすべて検証する。ユニットテストで検証できない以上、ここで検証しなければどこでも検証されないからである
- **切り出したルールが外側の層で使われていること。** ルールの中身はユニットテストで網羅するが、外側の層がその判定を呼び忘れてもユニットテストは通ってしまう。そのため、判定で却下される代表的なケースを1件だけ検証し、外側の層の結果（課金されない、状態が変わらない、など）を確かめる。ルールのすべてのパターンを繰り返さない
- **依存との契約。** SQL やクエリが実際の DB で意図どおりに動くこと、マイグレーション後のスキーマで読み書きできること

検証は、公開インターフェースを通して行う。
DB を使うテストでも、可能であれば DB の行を直接確認するのではなく、アプリケーションの読み取り操作を通して結果を確認する。
テーブル構造は実装の詳細であり、直接確認するとスキーマのリファクタリングでテストが壊れる。

前提データの準備（Arrange）も、公開されている操作があればそれを使う。
前提データを作る公開操作がない場合に限り、SQL などで直接データを投入してよい。
その場合も、結果の確認（Assert）は公開の読み取り操作を通して行う。

## 管理下の依存を本物で立てる

自分たちが管理する依存（自分たちのアプリケーションだけが使う DB、キャッシュ、キュー、ファイルシステムなど）は、モックせず本物を使う。
Docker（docker compose や Testcontainers など）でテスト用に立てる。

- **本番と同じ種類・バージョンを使う。** PostgreSQL の代わりに SQLite を使うなど、別物で代用すると、本番でだけ起きる差異を見逃す
- **スキーマは本番と同じマイグレーションで作る。** テスト専用のスキーマ定義を持たない
- **データはテストの開始時に用意し、片付ける。** 前のテストが途中で失敗しても、次のテストが影響を受けない。終了時の片付けだけに頼らない
- **テストどうしでデータを共有しない。** テストごとに必要なデータを作る。共通の初期データに依存すると、あるテストの変更が別のテストを壊す
- **並列実行するなら分離する。** テストごとにスキーマやデータベースを分ける、トランザクション内で実行して巻き戻すなどして、互いに干渉しないようにする

管理外の依存（外部API、外部SaaS、他チームのサービス）の扱いは [test-doubles.md](test-doubles.md) を参照。

## E2E テスト

E2E テストは、システム全体がつながって動くことを確かめるために少数だけ書く。
主要なユーザーの操作の流れに絞り、細かい条件の網羅はユニットテストに任せる。

E2E テストでも DAMP の方針は変わらない。
ログインやデータ登録のような前提を作る操作は共通化してよいが、検証対象の操作と期待値はテストケース内に書く（[damp.md](damp.md) を参照）。
