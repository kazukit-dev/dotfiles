# Principle Testing

テストの目的は、コードを変更しても振る舞いが壊れていないと確信できることにある。
この目的に反するテスト、つまり振る舞いが変わっていないのに壊れるテストは、価値よりもコストが大きい。
このスキルの方針はすべて、この一点から導かれている。

## 基本方針

### 1. 振る舞いを検証する

テストは公開インターフェースだけを通して対象を操作し、外から観察できる結果だけを検証する。
内部の手順、private な関数、呼び出し順序、中間状態は検証しない。
これらを検証すると、振る舞いを変えないリファクタリングでもテストが壊れる。

### 2. 変化しないテストを目指す

テストを修正してよいのは、機能そのもの（仕様）が変わったときだけである。

| 変更の種類 | テストへの影響 |
|---|---|
| リファクタリング | テストは修正しない。壊れたらテストが実装の詳細に依存している |
| バグ修正 | 既存のテストは修正しない。再現テストを追加する |
| 機能追加 | 既存のテストは修正しない。新しいテストを追加する |
| 仕様変更 | 変更された仕様に対応するテストだけを修正する |

仕様変更以外でテストを直す必要が出たら、そのテストの書き方自体を疑う。

### 3. 古典学派に従い、テストダブルは極力使わない

依存は本物を使う。テストダブルは、本物が遅い・結果が安定しない・テスト環境で使えないときに限って検討する。
使うのは管理外の依存の境界だけで、社内サービスの開発者が用意したフェイクがあればそれを使い、なければ（外部SaaSを含めて）モックを使う。フェイクを自分たちで書くことはしない。
インタラクションテスト（呼び出しの検証）は避ける。実装の詳細をテストに持ち込み、もろいテストを生むからである。
呼び出しを検証したくなったら、出力値ベーステスト、状態ベーステスト、インテグレーションテストの順に置き換えられないかを考える。
管理外の依存への副作用そのものが仕様である場合（メール送信、課金など）と、キャッシュのように呼び出しを抑えることが主な機能である場合に限って、インタラクションテストを使う。
テストダブルが多いテストは、もろいテストである可能性が高いと考えてよい。

詳細は [references/test-doubles.md](references/test-doubles.md) を読むこと。

### 4. ユニットテストを最も多くする

次の3条件をすべて満たすものをユニットテストとし、1つでも欠けるものはインテグレーションテストとする。

- 1単位の振る舞いを検証する
- 実行が速い
- 他のテストから隔離されている（順序や並列実行に関係なく同じ結果になる）

自分たちが管理する依存（DB など）はモックせず、Docker などで本物を立ててインテグレーションテストで検証する。
テスト全体では、ユニットテストの割合が他のどの種類よりも多くなるように設計する。
そのためには、ドメインロジックを I/O から切り離し、ユニットテストで検証できる形にしておく。

検証する内容は次のように分担する。

- **ユニットテスト**: ビジネス上の異常系（不正な入力、業務ルール違反、上限超過など）を、できるだけ多く検証する
- **インテグレーションテスト**: 業務シナリオごとに最も長いハッピーパスを1件と、ユニットテストでは検証できない異常系のすべてを検証する

詳細は [references/unit-and-integration.md](references/unit-and-integration.md) を読むこと。

### 5. バグは再現テストを先に書く

テストで再現できるバグは、修正の前に再現テストを追加し、それが失敗することを確認してから修正する。
失敗を確認しないと、そのテストが本当にバグを捉えているのか分からない。
自動テストで再現できないバグ（設定や実行環境に依存するものなど）や、テストの仕組みがないプロジェクトでは、再現テストを書かず、その理由を報告する。テストの仕組みは、頼まれない限り新しく作らない。テストを書く依頼だけでは、仕組みの導入を頼まれたとはみなさない。入れる場合の最小構成と予定しているテストケース名を示して、確認する。
再現テストを書かない場合も、修正の前にバグを手で再現し（既存のコマンドを実行するなど）、修正後に同じ手順で直ったことを確かめて、コマンドと結果を報告する。仕組みを入れるかどうかの確認では作業を止めず、報告の中で質問する。

バグの修正を頼まれた場合は、プロダクションコードを直してよい（「テストを書くときの手順」の2にある、変更案として示す扱いは当てはまらない）。報告には、手順7の内容に加えて、修正前に再現テストがどう失敗したか、修正の差分、修正後の実行結果を含める。

### 6. コードで表せない仕様はテストで表す

型や名前で表せない仕様（境界値の扱い、順序の保証、エラーになる条件など）は、テストで表せるならテストケースとして書く。
コメントやドキュメントは実装とずれても気づけないが、テストはずれた時点で失敗する。
テスト名を仕様文として読めるように書くのはこのためでもある。

### 7. テストは DAMP に書く

テストでは重複の削減よりも、読んだだけで意図が分かることを優先する。
検証に関係する入力値・操作・期待値は、各テストケースの中に書く。

詳細は [references/damp.md](references/damp.md) を読むこと。

## テストを書くときの手順

新しくテストを書くときの手順。バグの再現テストも、この手順で書く。

1. **検証する振る舞いを決める。** 仕様または対象コードを読み、公開インターフェースと、外から観察できる結果（戻り値、公開された状態、外部への副作用、例外）を洗い出す。
2. **依存を分類する。** 依存ごとに、本物を使えるか、管理下にあるかを判断する。管理下の依存は本物を使う。テストダブルが必要に見えたら、まず設計でロジックを依存から切り離せないかを検討する。
   - 切り出しなどプロダクションコードの変更が必要なら、黙って変更せず、変更案としてユーザーに示す。変更案は差分の形で示し、報告に理由を添える。変更を適用したファイルを別に用意したり、変更の経緯をコードのコメントに書いたりしない。
3. **テストの種類を決める。** ユニットテストの3条件を満たすかで判断する。満たさないものはインテグレーションテストにする。
4. **テストケースを洗い出す。** 正常系、境界値、異常系を挙げ、コードで表せない仕様が漏れていないかを確認する。ビジネス上の異常系はできるだけ多くユニットテストで検証する。インテグレーションテストでは、業務シナリオごとに最も長いハッピーパスを1件と、ユニットテストでは検証できない異常系のすべてを検証する。切り出した業務ルールについては、外側の層で判定が効いていることを代表的な1件で確かめる。
5. **テストを書く。** [references/test-design.md](references/test-design.md) の書き方に従う。既存のテストファイルに追加するときは、そのファイルのスタイル（1行で書くか AAA で区切るか、命名の形など）に合わせる。
6. **セルフレビューする。** 下のチェックリストで確認する。特に「内部構造を変えるリファクタリングをしたら、このテストは壊れるか」を自問する。
7. **報告する。** 追加したテストの一覧（ユニットとインテグレーションの別）、プロダクションコードの変更案（あれば差分と理由）、推測した前提と質問（「前提が分からないとき」を参照）を報告する。

再現テストだけを頼まれた場合は、プロダクションコードを変更しない。手順7の報告に、再現テストを実行した結果（どのテストが、どの値を期待して、実際に何が返って失敗したか）を加える。

## 前提が分からないとき

テストを書く、直す、レビューするときに、次のような情報が見えないことがある。

- 対象外の基盤（DB への接続方法、マイグレーションの実行方法、依存の注入方法など）
- 対象外の関数の仕様（戻り値の意味、例外を投げる条件など）
- 前提データを作る公開操作があるかどうか

その場合は、推測した前提に名前を付けてコードや修正案に書き、報告の中で一覧にする。
期待値が見えない仕様に依存するときは、一方の解釈で期待値を書き、その解釈を前提として明記する。
対象外の基盤そのもの（DB の起動設定、接続ヘルパーなど）は実装しない。前提として名前を挙げるだけにとどめる。
ユーザーが前提の誤りに気づけるようにするためである。

現在の振る舞いが仕様として疑わしいと感じても、黙って振る舞いを変えない。
テストは、ユーザーから示された仕様、なければ現在の振る舞いに合わせて書き、疑問点は報告の中で質問として挙げる。

## レビューのチェックリスト

テストコードのレビューを頼まれたら、次の観点で確認し、下の「レビューの出力」の形式で返す。

### 振る舞いと変化しにくさ

判断に迷ったら [references/test-design.md](references/test-design.md) を読む。

- [ ] 公開インターフェースを通じて、外から観察できる結果を検証しているか
- [ ] private な関数、内部の呼び出し回数や順序、中間状態を検証していないか
- [ ] 振る舞いを変えないリファクタリングで壊れないか
- [ ] 1つのテストで1つの振る舞いを検証しているか

### テストダブル

判断に迷ったら [references/test-doubles.md](references/test-doubles.md) を読む。

- [ ] 本物を使える依存にテストダブルを使っていないか
- [ ] 自分たちが管理する依存（DB、自チームのモジュール）をモックしていないか
- [ ] モックを使っているのは管理外の依存の境界だけか。自分たちで書いたフェイクを使っていないか
- [ ] インタラクションを検証している場合、出力値ベーステスト・状態ベーステスト・インテグレーションテストのどれでも検証できないか。検証しているのは仕様に当たる部分（宛先、回数など）だけか

### 種類と配分

判断に迷ったら [references/unit-and-integration.md](references/unit-and-integration.md) を読む。

- [ ] ユニットテストの3条件を満たさないものがユニットテストとして書かれていないか
- [ ] ロジックの分岐をインテグレーションテストで網羅しようとしていないか
- [ ] ビジネス上の異常系が、ユニットテストで十分に検証されているか
- [ ] ユニットテストでは検証できない異常系が、インテグレーションテストですべて検証されているか

### 読みやすさ

判断に迷ったら [references/test-design.md](references/test-design.md) と [references/damp.md](references/damp.md) を読む。

- [ ] テスト名が仕様文として読めるか
- [ ] 検証に関係する入力値・期待値がテストケース内に書かれているか
- [ ] テストの中に分岐・ループ・計算などのロジックがないか
- [ ] 失敗したとき、何が壊れたのかがメッセージから分かるか

### 実行の安定性

- [ ] 時刻・乱数・実行順序に依存していないか
- [ ] テスト間で状態を共有していないか

## レビューの出力

レビュー結果は次の形式で返す。

1. **要約**: 全体の評価と、最も重要な問題を2〜3行で書く
2. **指摘**: チェックリストの観点ごとに1件とし、重要度の高い順に並べる。同じテストに複数の観点が当たるときは分けて書く。1件ずつ次の4つを書く
   - 対象（テスト名と該当行）
   - 問題（チェックリストのどの観点に当たるか）
   - 理由（なぜ問題なのか。リファクタリングで壊れる、意図が読めない、など）
   - 修正案（コード、または手順）
3. **このままでよいテスト**: 一見問題がありそうでも、このスキルの例外に当たるもの（例：インタラクションテストを許可する条件に当たるもの）は、その根拠を添えてここに書く。補うとよいテスト（例：キャッシュが返す値を確かめる出力値ベーステスト）があれば、指摘ではなく任意の提案として添える
4. **前提と質問**: レビュー中に推測した前提の一覧と、ユーザーに確認したいこと（「前提が分からないとき」を参照）。なければ省く

修正案が、レビューの対象に含まれていないプロダクションコードに依存する場合は、その前提を修正案に明記する（例：「`createQuoteService` が DB を引数で受け取れない場合は、受け取れるように変更する」）。
